# ASW_Moderation

Reference moved out of `CLAUDE.md`. Learning from moderation: the single training point, the once-per-comment claim, rollbacks, the per-body lock, supersession, and the front-end "Mark as spam" link.

## `ASW_Moderation`

learns from moderation. There is exactly **one** training point, `transition_comment_status` (priority 10, 3 args), registered from `ASW::init()` next to `ASW_Privacy` and **not** gated on `is_admin()`: the link below and `admin-post.php` are not admin screens. Whatever moves a comment in or out of the spam queue — the Comments-screen row action, a bulk action, another antispam plugin, the plugin's own Spam Log pill, the "Mark as spam" link this class renders — fires it, so there is no second place to keep in sync. `on_transition()` teaches **spam** on `new === 'spam' && old !== 'spam'` and **ham** on `old === 'spam' && new is 'approved' or 'unapproved'`; every other transition (to `trash`, any approval that does not come out of the spam queue, and `spam → spam`, which core itself short-circuits) returns untouched. Accepting `spam → unapproved` as ham is load-bearing, not generosity: `wp_unspam_comment()` restores the status recorded in the `_wp_trash_meta_status` comment meta and falls back to `'0'` (unapproved) when it is absent, and it is absent for exactly the comments this plugin flagged — detection returns `'spam'` from `pre_comment_approved`, so the row is *inserted* as spam and never passes through `wp_spam_comment()`, which is what writes that meta. Matching only `'approved'` left the single most valuable ham signal — a moderator clicking **Not Spam** on one of the plugin's own false positives — teaching nothing at all (`ModerationTest::test_not_spam_on_a_comment_the_plugin_blocked_trains_ham` pins it, and `…test_transitions_that_teach_nothing_store_nothing` pins the other side: a held or untrashed comment being approved is not a Not Spam decision). The payload must be an object with a positive `comment_ID`, and its `comment_type` must be empty or `'comment'` — the same scope as `ASW_Detector::filter_comment()`, which refuses pingbacks and trackbacks; without that guard a bulk spam action over a batch of pingbacks filled the corpus with site titles and post excerpts the plugin never classifies. The body is normalised with the same `preg_replace( '/(*UCP)\s+/u', ' ', … )` + `trim()` as `ASW_Admin_Page::ajax_mark_comment()` — an empty result teaches nothing and creates no entry.
A **spam** verdict on a comment with no Spam Log entry creates one first, `add_entry( $content, array( self::CHECK_NAME ), $ip_hash, $comment_id )` with `CHECK_NAME = 'manual'` (badged "Marked by moderator" by `settings-log.php`, `mod => 'duplicates'`) and `ASW_Detector::hash_ip()` — `''` when the comment carries no IP. That is the whole point of the feature: a comment that passed every check is the case that most needs teaching and is exactly the one with no entry. Marking as **ham** never creates an entry — the plugin has nothing to answer for there — so a ham claim on such a comment comes back `'not_found'` and proceeds unlocked, which is harmless because samples are deduplicated by content.
The lock is the entry's `trained_as` flag, claimed through `ASW_Spam_Log::claim_training()`: `'already_trained'` returns immediately, which is what makes the AJAX pill and the transition the pill itself fires store **exactly one** sample **in either order** (`ModerationTest` pins both orders, and `MarkCommentTest` passes unchanged). The sample is stored exactly as the pill stores it — `ASW_Script_Detector::detect( $content )`, then `$repository->insert( $script, $category, $content, $comment_id, ASW_Detector::hash_email( $comment->comment_author_email ) )` — so `ASW_Privacy` reaches it by both subject keys and `uninstall.php` is unaffected (no new storage location).
The pill performs the same opposite-category delete, **after** its status change rather than before it. Its `mark_trained()` claim is per comment, not per text, so a comment whose body is already trained as the other category from a *different* comment claims cleanly and inserts — and when the comment is already at the target status (confirming **Spam** on a comment the plugin already moved to the spam queue: the common case on that screen) `wp_spam_comment()` is skipped, no `transition_comment_status` fires, and `ASW_Moderation` never runs, so nothing else would ever remove the opposite row. Permanently: the claim then answers `'already_trained'` and `mark_trained()` refuses to overwrite it, so the pill offers no retry either. The reconciliation runs *after* the status change rather than before it, and on **both** outcomes; a `false` from the delete (a refused DELETE, not "nothing matched") rolls the claim back with `unmark_trained()` so the retry the pill then offers re-runs an `insert()` that dedups and a delete that clears the contradiction. A **failed status change releases the claim and keeps the stored sample** — it never deletes the row its own `insert()` created, the rule `ASW_Moderation::roll_back_claim()` follows as well. That row is shared state, not this request's property: the table dedups on content, the lock cannot be held across the status change, and another moderation of the same body (one bot body posted from many addresses is routine) can be answered `'exists'` in that window and commit against this very row — deleting it then pulled the sample out from under *that* request's claim, which every later transition of its comment reads as `'already_trained'`, a silent loss on a comment this request has nothing to do with. Because that row is kept, the opposite-category delete has to run on the failed-status path too: a kept row beside an untouched opposite row **is** the text trained as both categories, so skipping the reconciliation there left that contradiction behind for a later moderation to clear. It is therefore the first thing the second lock section does, and the failed status change only decides whether the claim goes back and what the moderator is told (`MarkCommentTest::test_a_failed_status_change_releases_the_claim_and_keeps_the_sample` pins all three halves — the kept row, the reconciled opposite row and the released claim). `MarkCommentTest::test_marking_a_comment_already_at_the_target_status_deletes_the_opposite_sample`, `…test_a_refused_opposite_delete_rolls_the_claim_back_so_the_pill_can_retry` and `…test_the_pill_takes_the_per_body_moderation_lock` pin the rest of it — the reconciliation on the no-status-change path, the rollback a refused delete takes, and the shared lock. Because the lock cannot be held across the status change, that reconciliation is a **second** acquisition, and another moderation of the same body can commit the opposite category in between — inserting its row and removing with its own flip the row this request stored — after which deleting the opposite blindly left the text trained as **neither** while both log claims stood. The second section therefore re-reads `find_categories_by_hash( $script, $content_hash )` inside the lock and issues the delete **only on the positive evidence that both categories are present**; every other reading leaves the table alone. This request's category gone and the opposite one there is a newer decision it stands down from, exactly as `transition_is_current()` makes a superseded transition stand down (`…test_a_superseded_pill_leaves_the_newer_decisions_sample_alone` pins it); no opposite row is nothing to delete (one query fewer than the unconditional DELETE this replaces); and an **empty result the database refused** — `find_categories_by_hash()` reports a failed read as no rows, indistinguishable from "nothing stored" — is an unknown state in which deleting would re-open the very "trained as neither" race the re-read exists to close, so no row is ever removed on the strength of a read that failed (`…test_a_failed_supersession_read_deletes_nothing` pins it). Not deleting leaves at most the contradiction, and the next moderation of either comment clears that, since `ASW_Moderation::training_is_settled()` refuses a claim whose opposite row is present. All four of the pill's claim rollbacks go through `clear_training_claim()`, which checks the `bool` `ASW_Spam_Log::unmark_trained()` returns and logs `ASW: training rollback failed for comment <id>` (an int, no user input) on a refused write — the same loss `ASW_Moderation::roll_back_claim()` reports, and final on this screen, since `mark_trained()` refuses an entry that already carries a category; what recovers it is `ASW_Moderation::commit_training()`'s verification on the next moderation. **Every** one of them is reported to the moderator rather than returned as the plain "try again" the pill would then answer `'already_trained'`: the failed-status path keeps its own `Comment status could not be changed and rollback failed. Please check training data manually.` msgid, and the three that are not about the status — a null repository, a refused `insert()` and a refused flip delete, where the status did change — report `Training data may be inconsistent. Please check training data manually.`, the one new POT entry this adds (`…test_a_refused_claim_rollback_on_a_failed_status_change_is_reported`, `…test_a_refused_claim_rollback_after_a_refused_insert_is_reported` and `…test_a_refused_rollback_after_a_refused_flip_delete_is_reported` pin the three).
A category flip deletes the opposite category's row (`delete_by_hash( $script, $opposite, hash( 'sha256', $content ) )`) **after** the insert succeeded, never before: a failed insert must not leave the table short a row. The two-way rollback keyed on the claim keeps the log from contradicting the table — claim `'ok'` + failed insert → `unmark_trained()` (nothing is stored, so untrained is the truth); claim `'flipped'` + failed insert → `restore_training( $comment_id, $opposite )`, because the delete never ran and the *old* category's sample is still stored, so clearing the flag would show an untrained comment that is in fact trained as the other category; claim `'not_found'` → nothing to undo. A null repository takes the same rollback. Three more failures take it as well, for the same reason — a claim left standing comes back `'already_trained'` on every later transition, so the loss would be **permanent**: a `delete_by_hash()` that returned **`false`** (a refused DELETE, not "nothing matched" — leaving the claim would keep that text trained as *both* categories for good; `ModerationTest::test_a_failed_flip_delete_rolls_the_claim_back_so_the_next_moderation_retries` pins it, and the retry is safe because `insert()` dedups to `'exists'`), and a **throw** anywhere past the claim — the insert, the delete, `ASW_Script_Detector::detect()` — which is caught inside `train()`, rolled back and **rethrown** so `on_transition()`'s fail-open catch still writes its sanitized diagnostic (`…test_a_throwing_repository_does_not_fatal_the_moderation_action` pins the rollback and the retry after it). A claim whose own option write was refused is reported `'failed'` by `claim_training()` rather than `'ok'`/`'flipped'` or `'not_found'`, and `train()` returns on it **without touching the repository**: nothing was claimed, so there is nothing to restore, and training unlocked under a log entry that still names the other category is the one failure that would be permanent (see the `ASW_Spam_Log` bullet). A rollback whose own write is refused is the mirror image — the claim stands over a training that never happened, every later transition reads `'already_trained'`, and no other signal on the site shows it — so `roll_back_claim()` checks the `bool` the two log writers now return and logs `ASW: moderation training rollback failed for comment <id>` (an int, no user input); there is no second write to attempt, since the option store is what just refused one, and the Spam Log pill cannot clear it either — `mark_trained()` refuses an entry that already carries a category, so that one lever is closed too. What keeps the loss from being permanent is that the `'already_trained'` claim is **verified** against the table: `training_is_settled()` believes it only when the one `ASW_Sample_Repository::find_categories_by_hash( $script, $content_hash )` lookup shows this text stored **in this category** *and* **not in the opposite one**, so the next moderation of a comment whose rollback was refused finds nothing behind the flag and trains anyway (`ModerationTest::test_a_refused_rollback_is_reported_because_it_blocks_every_later_retry`, `…test_a_claim_left_by_a_refused_rollback_does_not_block_the_next_moderation` and `…test_a_stale_claim_is_verified_against_the_category_the_table_holds` pin the three halves — the diagnostic, the recovery, and that matching the *category* is what recovers a refused flip, where the table still holds the opposite category's sample). Requiring the opposite row's **absence** is the other half of the same recovery, and it is the one case the claim-rollback alone cannot reach: a flip whose `delete_by_hash()` was refused has already inserted the new category's row, and the rollback restores the log to the *old* category — after which the next teaching transition is necessarily back to that old category, so a check on the claimed row alone would short-circuit and leave the text trained as **both** categories for good, the exact state the flip delete exists to prevent. Falling through instead re-runs an `insert()` that dedups to `'exists'` and a `delete_by_hash()` that finally clears the contradiction (`…test_a_stale_opposite_sample_left_by_a_failed_flip_delete_is_cleaned_up` pins it). The lookup is keyed on the **sample identity** — `(script, content_hash)`, the unique key `insert()` and `delete_by_hash()` write — and deliberately **not** on `comment_id`: content dedup keeps only the *first* comment's `comment_id` on a row, so a second comment carrying identical text (one bot body sent from many addresses, routine) trains the row the first one created, and a comment-keyed check would be asking about a row this commit never writes — the opposite-category row left by a refused flip delete could belong to the other comment, be invisible to the lookup, and the claim would be reported settled while the text stayed trained as both categories for good (`…test_an_opposite_sample_owned_by_another_comment_with_the_same_text_is_cleaned_up` pins it). One query answers both questions, so a caller cannot see a half-failed read. The verification costs one indexed lookup on a path that only runs when a comment is moderated twice in the same direction (the pill and the transition it fires being the usual pair), and it errs toward a redundant `insert()` — which dedups by content hash — rather than a skipped one: a failed read comes back as an empty array and reports "not settled". An opposite-category row left from a body that has since been edited carries a different hash, so it is neither seen here nor touched by the `delete_by_hash()` the fall-through runs. The next moderation retries in every case, and the `manual` entry this call may have created is deliberately **kept** on failure: it records what the moderator did, and with the flag cleared, restored or verified away the training is reachable again.
The claim and the sample write together are serialised **per comment body** through `ASW_Moderation::with_body_lock( $content, $critical )`, which holds an exclusive `flock` on `.asw-locks/asw_moderation_<md5(ABSPATH)>_<bucket>.lock` — a bounded pool of 256 buckets keyed off `md5( $content )`, the same shape as `ASW_Duplicate_Check`'s, so the directory cannot grow one file per comment — releasing in a `finally` like every other lock site; `train()` runs `transition_is_current()`, the claim, the insert and the flip delete inside it. The helper is **shared with the second writer of the sample table**, the Spam Log's AJAX pill (`ASW_Admin_Page::ajax_mark_comment()`), which takes it around its `mark_trained()` claim plus `insert()` and again around the opposite-category delete below, so the two writers serialise against each other rather than each committing half a flip. A caller must not change a comment's status **inside** the callback: `wp_update_comment()` fires `transition_comment_status` synchronously, `train()` re-enters the helper through a *second* file handle, and `flock()` locks the open file description rather than the process — so the nested acquisition would block on the outer one for the rest of the request. That is why the pill releases the lock before `wp_spam_comment()`/`wp_unspam_comment()` and re-takes it afterwards. The lock alone would not settle two overlapping moderations (a Comments-screen **Spam** click and the **Undo** that overtakes it): each would claim in turn, and the one that claimed first could still insert its category and delete the other's afterwards, leaving the comment and the log saying one thing and the sample table the other. The key is the normalised **body**, not the comment id, because the body is what the commit mutates: `insert()`/`delete_by_hash()` address rows by `(script, category, content_hash)` and the script is a function of the content, so hashing the body covers exactly the rows one call can touch, while the same comment still serialises against itself (its two transitions carry the same body). Keying by comment id instead left two comments carrying identical text moderated in **opposite** directions under *different* locks: both inserted their category and each then deleted the other's row, leaving the text trained as neither while both log claims stood (`…test_comments_with_identical_text_take_the_same_moderation_lock` pins the key). What settles the same-comment case is re-reading the comment row **inside** the lock: WordPress writes the row and *then* fires `transition_comment_status`, so whichever callback takes the lock second sees the newer `comment_approved` and stands down. That read must reach the **database**, so `transition_is_current()` calls `clean_comment_cache( $comment_id )` first: `get_comment()` answers from the object cache (`WP_Comment::get_instance()`), and WordPress's default cache is **request-local** — `wp_set_comment_status()` repopulated this request's copy from its own write just before firing the hook, and the concurrent request that committed the newer status ran in another process where it could not touch it, so without the clean the guard would compare `$new_status` against the very row that produced it and always agree. `ModerationTest::test_a_superseded_transition_is_not_hidden_by_a_cached_comment` pins it through the bootstrap's `$wp_comment_cache` stub (which `get_comment()` consults ahead of the `$wp_comments` fixture, and `clean_comment_cache()` — and `asw_test_set_comment_status()`, as core's `wp_update_comment()` does — drops), since the fixture-reading stub alone cannot express a stale snapshot. `transition_is_current()` compares it against the `$new_status` the callback was fired for, normalising `1`/`approve` → `approved` and `0`/`hold` → `unapproved` exactly as core does, and **stands down when the comment can no longer be read at all** (hard-deleted between the transition and the call, by a concurrent request or by an earlier hook on the same action) rather than failing open: the `manual` Spam Log entry it would create is keyed by `comment_id` alone — unlike a sample, which also carries the salted `email_hash`, and unlike a form entry — and `ASW_Privacy` reaches comment entries only by looking the subject's comments up, so an entry written for a row that no longer exists could never be exported or erased and its fragment and IP hash would outlive every request that could reach them; its pill would be dead too, since `ASW_Admin_Page::ajax_mark_comment()` refuses a comment it cannot load, and there is no moderator decision left to preserve either way. `ModerationTest::test_a_superseded_transition_does_not_train_over_the_newer_decision` pins both halves of the status case: the stale callback teaches nothing and creates no `manual` entry, and the same call once the row really does say `spam` trains normally; `…test_a_comment_that_no_longer_exists_creates_no_record` pins the deleted case the same way.
The whole of `on_transition()` is a `try/catch(\Throwable)` around a private `train()`, following `ASW_Detector::run()` and `ASW_CF7_Integration::filter_spam()`: it runs inside `wp_set_comment_status()`, and `add_entry()`/`claim_training()` call `update_option()`, so a third-party `pre_update_option_*` filter or a `$wpdb` failure throwing here would fatal the Comments screen in the middle of a moderation action. The diagnostic logs `basename( $e->getFile() ) . ':' . $e->getLine()` and **never `$e->getMessage()`**, and `ModerationTest::test_the_fail_open_diagnostic_never_logs_the_exception_message` pins that on the catch block's source text by enumerating every use of `$e` (a name-only grep for `getMessage()` is passed unchanged by `. $e` or `"{$e}"`). `append_moderation_link()` takes `$text` **untyped** and returns it unchanged when `! is_string( $text )`: the plugin does not declare `strict_types`, but a userland `string` parameter still `TypeError`s on `null`, and an earlier `comment_text` filter returning null is an ordinary third-party bug that would otherwise fatal the whole post page — the same rule as `ASW_Detector`'s `is_string()` guards.
## The "Mark as spam" link

`append_moderation_link()` on `comment_text` at **priority 100** (2 args), plus `wp_enqueue_scripts` and both `admin_post_asw_mark_spam` and `admin_post_nopriv_asw_mark_spam` (`ACTION = 'asw_mark_spam'`); the *nopriv* registration is what turns a logged-out or expired-session click into the handler's own 403 instead of WordPress's generic "invalid action". Priority 100 is load-bearing: core hangs `convert_smilies` (20), `force_balance_tags` (25), `wpautop` (30) and `capital_P_dangit` (31) on `comment_text` (`wp-includes/default-filters.php`), so a `<p><a>` block appended at 10 would be re-processed by `wpautop`; at 100 the appended markup is the last thing touched, the reason is carried as a one-line comment at the `add_filter()` call, and `ModerationLinkTest` asserts the priority off `$GLOBALS['wp_filters']['comment_text']` (the stub bootstrap has no `has_filter()`). The filter returns `$text` **byte-identical** unless all of `current_user_can( 'manage_options' )` (checked **first**, so an anonymous page load pays one capability call and nothing else), `! is_admin()`, `! is_feed()`, not `REST_REQUEST`, an object with a positive `comment_ID`, `'spam' !== comment_approved`, and `! ASW_Shadow_Display::is_shadowed( $comment_id )` hold. The last one decides on the **real** status: a comment the shadow display presents to its own author arrives here as a per-request clone carrying `comment_approved = '0'` while the row is `spam`, so the presented value alone would offer an administrator viewing their own flagged comment a "Mark as spam" link on a comment that already is (`ModerationLinkTest::test_no_link_under_a_shadow_displayed_comment`, `…test_the_link_still_renders_under_an_ordinary_comment_beside_a_shadow_one`; see `docs/shadow-display.md`). The markup is `<p class="asw-moderate"><a class="asw-moderate-link" href="…">Mark as spam</a></p>` with the href from `wp_nonce_url( add_query_arg( … admin_url( 'admin-post.php' ) ), self::ACTION . '_' . $id )` — the nonce is bound to that **one** comment, so a link harvested from one cannot be replayed against another. No JavaScript. `enqueue_styles()` enqueues the **shared** `asw-comment-form` handle (`ASW_URL . 'public/css/comment-form.css'`, `ASW_VERSION`) for a `manage_options` user on `is_singular()`, so a page rendering both the bot fields and the link loads the file once; `.asw-moderate`/`.asw-moderate-link` are a deliberately minimal small/secondary/inherited-colour rule so they do not fight the theme. `handle_mark_spam()` runs **capability → nonce → comment**, in that order: `wp_die( …, array( 'response' => 403 ) )` before the nonce store is ever consulted (pinned), then the `comment_id` read (an annotated `phpcs:ignore WordPress.Security.NonceVerification.Recommended`, unavoidable because the id is what the nonce action is built from), then `check_admin_referer( self::ACTION . '_' . $comment_id )`, then `get_comment()` with a 404 `wp_die()` reusing the `Comment not found.` msgid `ASW_Admin_Page` already ships (so the link adds only `Mark as spam` and `You do not have permission to moderate comments.` to the POT). It calls `wp_spam_comment()` only when the comment is not already spam and does **no training of its own** — the transition hook above is the single training point — and a `false` from it is a refused `wp_update_comment()`: no status written, no transition, nothing trained, so the handler `wp_die()`s **500** reusing `ASW_Admin_Page`'s existing `Comment status could not be changed. Please try again.` msgid (again no new POT entry) rather than redirecting the moderator back to a page where the comment is still visible with no sign the click did nothing (`ModerationLinkTest::test_a_failed_status_change_is_reported_instead_of_redirecting` pins it, driven by the bootstrap's `$wp_comment_status_change_fails` switch). On success it then `wp_safe_redirect( get_permalink( comment_post_ID ) ?: home_url( '/' ) )` behind the usual `// @codeCoverageIgnoreStart` + `if ( ! defined( 'ASW_TESTING' ) ) { exit; }` guard. Known non-coverage: a theme or comment plugin that renders comment bodies without the `comment_text` filter (wpDiscuz, Disqus and friends) shows no link — the transition training still works there, because it hooks WordPress's own status change rather than any UI
