# Test bootstrap stubs

Reference moved out of `CLAUDE.md`. What `tests/bootstrap.php` stubs, which globals switch each stub's behaviour, and which test depends on which switch. Keep it in sync when a stub or switch is added.

Uses PHPUnit 9.6 via Docker Compose. Tests bootstrap (`tests/bootstrap.php`) provides WordPress function stubs — no real WordPress instance needed. Stubs of note for coverage tests: `is_singular()` and `comments_open()` (switchable via `$GLOBALS['wp_is_singular']` and `$GLOBALS['wp_comments_open']`, defaulting to true, to test stylesheet enqueue conditions); `date_i18n()` (delegates to `gmdate()` so view rendering of a populated log does not fatal); `wp_using_ext_object_cache()` is switchable via `$GLOBALS['wp_using_ext_object_cache']` (defaults false — set true to exercise the duplicate-check external-cache path); `set_transient()` records into `$wp_transients`, mirrors into `$wp_options['_transient_…']` and injects a `__ttl` member into any **array** value (which is how `DuplicateCheckTest` reads back the recorded expiry, and why `ASW_Duplicate_Check::read_transient_data()` must tolerate a non-array top-level member), while the `wp_cache_*` stubs write into that **same** `$wp_transients` global under `"{$group}:{$key}"` — so the object cache's `asw:asw_dup_…` counters and the file-locked path's bare `asw_dup_…` maps live side by side and are told apart by prefix, which is what lets `DuplicateCheckTest` assert that each path writes only its own storage; paired with it, the `wp_cache_incr()` stub honors `$GLOBALS['wp_cache_incr_force_false']` (return false that many times to simulate the key being evicted between `wp_cache_add()` and `wp_cache_incr()`) and `$GLOBALS['wp_cache_incr_evict_on_force']` (also unset the key so the subsequent re-`add()` succeeds) — together these exercise the duplicate-check eviction-recovery / fail-open branches, and both default to unset so existing tests are unaffected; and the `$wpdb` stub lets a test inject `insert`/`delete` return values (`$wpdb->insert_result` / `$wpdb->delete_result`, both reset to `null`/prior behavior between tests) to simulate DB failures in `ASW_Sample_Repository`. When an insert is forced to fail, `$wpdb->insert_writes_on_forced_failure` selects which failure mode is modeled: true = a concurrent request still wrote the row (the repository's post-insert recheck finds it and returns `'exists'`), false = a genuine DB error (no row written, `insert()` returns false). The forced-failure gate is a strict identity check (`false === $this->insert_result`, matching `delete()`), so a test must inject exactly `false` to force failure — a falsy `0` does not trigger it. For the WordPress Privacy API tests (`ASW_Privacy`): the `get_comments()` stub filters the `$wp_comments` fixture by `author_email` and by `comment__in` (the id whitelist `ASW_Privacy::comment_ids_on_later_pages()` uses), models WP's `status` semantics (default `all` matches only held/approved and excludes `spam`/`trash`; `any` matches every status — a fixture comment without an explicit `comment_approved` is treated as approved) and honors `number`/`paged` pagination and `fields => 'ids'`; `wp_add_privacy_policy_content()` records each call into the `$wp_privacy_policy_content` global (`['plugin_name', 'policy_text']`) for assertion; and `wp_kses_post()`/`wpautop()` are pass-through/minimal stubs. CF7 stubs (`WPCF7_ContactForm::get_current()`/`id()`/`scan_form_tags()`, `WPCF7_FormTag` with `$name`/`$basetype`, `WPCF7_Submission::get_instance()`/`get_contact_form()`/`get_posted_data()`/`get_meta()`/`add_spam_log()` recording into `$wp_cf7_spam_log`, plus `is_email()` and globals `$wp_cf7_current_form`/`$wp_cf7_form_id`/`$wp_cf7_form_tags`/`$wp_cf7_submission`/`$wp_cf7_submission_form`/`$wp_cf7_posted_data`/`$wp_cf7_meta`/`$wp_cf7_remote_ip`/`$wp_cf7_is_available`/`$wp_cf7_spam_log`) are `class_exists`-guarded and driven by globals so tests can simulate CF7 present/absent; `$wp_cf7_is_available` forces `ASW_CF7_Integration::is_available()` false when set to false, and `is_email()` delegates to `filter_var` validation in tests. The admin-menu stubs return the **real** hook suffixes WordPress would generate, so asset-enqueue gating can be tested faithfully: `add_menu_page()` returns `'toplevel_page_' . $menu_slug`, and `add_submenu_page()` mirrors `get_plugin_page_hookname()` by prefixing with `sanitize_title()` of the *parent's menu title* (recorded in `$wp_menu_pages`) — `'AntiSpam Wizard'` → `antispam-wizard_page_{slug}`, **not** the parent slug — falling back to the parent slug when the parent is not a registered top-level menu; a minimal `sanitize_title()` stub backs this. Consequently a test that exercises `ASW_Admin_Page::enqueue_assets()` must call `add_menu_page()` first, since the class stores the hook suffixes returned by those calls rather than reconstructing them. The `$wpdb` stub's `prepare()` models WordPress's placeholder rendering: it matches `%s|%d|%i` and renders `%i` as a backtick-quoted identifier with embedded backticks doubled (`` `wp_asw_samples` ``), `%s` single-quoted, and `%d` as a bare `(int)` — **unquoted, as real WordPress does**, which is what makes a `%d`→`%s` slip in repository code visible to the `prepared_queries` assertions instead of rendering identically. The stub's WHERE parser (shared by `get_results()`/`get_var()` and by `query()`) understands `col IN ('a','b')` / `col IN (5, 6)` as well as `col = 'val'` / `col = 5` — the bare-number forms exist because `%d` renders unquoted —, consuming the IN lists from the query text first so their quoted values cannot be mis-read as equality conditions by the `=` scan that follows; and `query()` executes a `DELETE FROM <table> WHERE …` against the in-memory table, returning the number of rows it removed while every other query still returns `true` (the revision-bump `UPDATE` branch is unchanged) — so its return type is `int|bool`, matching the real `wpdb::query()`. That is what lets `ASW_Sample_Repository::find_by_comment_ids()` / `delete_by_comment_ids()` (and their `…_by_email_hash()` twins) be tested end to end without a database. Their DB-failure branches are reachable too: `$wpdb->suppress_errors()` mirrors the real method (sets the flag, returns the previous value) and `$wpdb->on_get_var` is a callable invoked at the top of `get_var()` with the query, which is how `SampleRepositoryTest::test_schema_probes_run_with_wpdb_errors_suppressed` observes `$suppress_errors` *while* a probe runs rather than after the `finally` restored it; `$wpdb->on_get_results` is its counterpart at the top of `get_results()`, which is what lets `…test_script_fingerprint_runs_with_wpdb_errors_suppressed` observe the same bracket around `script_fingerprint()`'s `SELECT`; all three are cleared by `reset_tables()`. `get_results()` also answers **aggregate** queries — `SELECT <col>, COUNT(*) AS <alias>, MAX(<col>) AS <alias> FROM <table> WHERE … GROUP BY <col>`, exactly the shape `ASW_Sample_Repository::script_fingerprint()` emits — from the in-memory table, grouping the `filter_rows_by_where()` survivors by the `GROUP BY` column and projecting the SELECT list through `project_aggregates()`. That branch is placed **before** the generic `SELECT … FROM` branch, which would otherwise return the raw rows, and a group with no matching rows produces **no row at all**, as real SQL does — never a zero-count row, which is what makes the fingerprint's `0:0` rendering testable; `$wpdb->get_results_result = false` still returns `null` ahead of it, so the failed-read path stays reachable. `get_transient()` appends its key to the `$wp_transient_reads` global on **every** call, hit or miss, in call order (initialised at bootstrap, reset per test), which is how `ModelStoreTest` and `ASWTest` assert that a submission reads exactly one `asw_classifiers_*` key and which one. `delete_transient()` returns **whether the key was there** (as real WordPress does) and honours `$GLOBALS['wp_transient_delete_fails']` (default false, also accepts an array of transient names) to model a backend that refused the delete — the value stays put and `false` comes back, which is also what a key that was never there returns, so a caller that must tell the two apart has to read the key back; that switch is what reaches `ASW_Model_Store::delete_units()`'s remediation ladder and, with the writes below refused as well, `ASW_Privacy::erase()`'s cache-purge `items_retained`. `set_transient()` additionally calls `$GLOBALS['wp_on_set_transient']` (default null) just **before** the write lands, which is the only way to model another request committing in the window between a writer's pre-write fingerprint check and its own `set_transient()` — the write then happens on top of whatever that other request did, which is the erasure race `ModelStoreTest` drives through it; the seam fires **before** the write is attempted, and `set_transient()` now honours the existing `$GLOBALS['wp_update_option_fails']` switch against the option name it really writes (`_transient_<name>`) — real `set_transient()` stores through `add_option()`/`update_option()`, so the same switch models a backend that refused the write, and checking it *after* the seam is what lets a callback arm the refusal for the **next** write rather than the one it is standing in (the post-write blanking write `ASW_Model_Store` attempts). The three transient stubs honour `wp_using_ext_object_cache()` the way core does: without an external cache a transient *is* the `_transient_<name>` option row (read, written and deleted as one), and with one it lives in the cache alone — `set_transient()` creates no option row, `delete_transient()` leaves any row of that name exactly where it is, and `get_transient()` cannot see it. That is what makes a row stranded by an object cache installed after the fact reachable only by `ASW_Model_Store`'s prefix sweep, and it is why the `$wp_update_option_fails` switch applies to `set_transient()` only on the option-backed path. The `$wpdb` stub's `query()` also executes `DELETE FROM <options> WHERE option_name LIKE '…'` against the `$wp_options` global (honouring an `option_name NOT IN ( … )` exclusion and `esc_like()`'s `\_`/`\%` escapes, and dropping the mirrored `$wp_transients` entry), since `wp_options` is not one of its in-memory tables — that is what lets `uninstall.php`'s pattern delete and `ASW_Model_Store::delete_stray_rows()` be driven without a database. `$GLOBALS['wp_transient_expired']` (default false, also accepts an array of transient names) makes `get_transient()` behave as core does for an expired database-backed transient: it deletes the row — honouring the delete-refusal switch above — and reports a miss **whether or not that cleanup landed**, so a `false` from `get_transient()` is not proof the row is gone, which is exactly why `ASW_Model_Store::delete_units()` reads the `_transient_…` option row directly. `$wpdb->query_result` and `$wpdb->get_results_result` are strict-`false ===` injection hooks (reset by `reset_tables()`, mirroring `insert_result`/`delete_result`) that make `query()` return `false` and `get_results()` return the **empty array** the real `wpdb` does on an error, with `$wpdb->last_error` set — `wpdb::query()` flushes `last_result` to `array()` before running and returns `false` without touching it again, so a failed read is indistinguishable from "no matching rows" by return value alone and a caller that must tell them apart has to read `last_error` (the stub clears it at the top of every `get_results()`, as `flush()` does). The repository's other readers all answer `array()` either way, so only `script_fingerprint()` needs it; the return type stays untyped because the no-query early return still yields `null`. The `dbDelta()` stub records every DDL it is handed into the `$wp_dbdelta_queries` global, so `ASWTest` can assert that `ASW::maybe_upgrade_schema()` re-runs the DDL when the stored schema version is behind and stays a no-op when it matches; it also **applies** the DDL's column names *and named index names* into the `$wpdb` stub, which is what `SHOW COLUMNS FROM <table> LIKE '<col>'` (answered by `get_var()`, unescaping `esc_like()`'s `\_`) and `SHOW INDEX FROM <table> WHERE Key_name = '<idx>'` (also `get_var()`, returning the table name for a hit and `null` for a miss, as real MySQL does — `SHOW INDEX` has no `LIKE` form) read. Two independent refusal switches model the two ways a migration half-lands: `$wp_dbdelta_applies = false` is a database that refused the statement outright, i.e. `dbDelta()` returning normally while the column never appears; `$wp_dbdelta_index_applies = false` is the subtler one — the `ADD COLUMN` landed and the `ADD KEY` did not, which real `dbDelta()` cannot distinguish because it fires them as separate `ALTER`s and checks neither. Between them they are the only way to reach `ASW_Sample_Repository::schema_is_current()`'s false branches. `reset_tables()` restores both switches (and clears the recorded columns and indexes) alongside the other injected stub state, so a refusal cannot leak between tests; `ASWTest::setUp()` calls it for that reason. `wp_spam_comment()`/`wp_unspam_comment()` are no longer inert setters: both route through the exported `asw_test_set_comment_status( $comment_id, $new_approved )`, which writes the new `comment_approved` and then fires `transition_comment_status` with core's normalisation (`1`/`approve` → `approved`, `0`/`hold` → `unapproved`, `spam`/`trash` unchanged) and core's early return when the new status equals the old one — so **any** test that spams or unspams a comment now also runs `ASW_Moderation`'s training, which is what makes `MarkCommentTest`'s pill-then-transition invariant real. `$GLOBALS['wp_comment_status_change_fails']` (default false) makes that helper — and therefore both wrappers — model a refused `wp_update_comment()`: no status written, no transition fired, `false` returned, which is the only way to reach `ASW_Moderation::handle_mark_spam()`'s failed-status-change branch. `$GLOBALS['wp_delete_comment_meta_fails']` (default false) makes `delete_comment_meta()` refuse the DELETE and return false — the same value core returns for a key that was already absent — which is how `ShadowDisplayTest::test_forget_verdict_reads_back_a_refused_delete_and_logs_it` reaches `ASW_Shadow_Display::forget_verdict()`'s read-back. `$GLOBALS['wp_update_comment_meta_fails']` (default false) makes `update_comment_meta()` refuse the write and return false with the stored value kept; `true` refuses every write, a callable `( $comment_id, $meta_key, $meta_value )` refuses only the writes it returns true for — which is how `MarkCommentTest::test_a_refused_trash_status_rollback_is_logged` lets `ASW_Admin_Page::move_out_of_spam()`'s first `_wp_trash_meta_status` write land and refuses the rollback (`BootstrapStubsTest::test_update_comment_meta_can_be_made_to_refuse`); `MarkCommentTest` resets it. `$GLOBALS['wp_update_option_fails']` (default false, also accepts an array of option names) makes `update_option()` refuse the write and return false, which is how `SpamLogTest` reaches `ASW_Spam_Log::claim_training()`'s failed-write branch. The helper is exported so a test can drive any transition directly, not just the two those wrappers cover; `wp_spam_comment()` records the previous `comment_approved` in `_wp_trash_meta_status`, and `wp_unspam_comment()`/`wp_untrash_comment()` restore that value, fall back to `'0'` when it is absent and drop the meta on success, exactly as core does — so a comment flagged on submission lands **unapproved** on Not Spam, and a comment trashed from the spam queue (`_wp_trash_meta_status = 'spam'`) would be restored to `spam`. The stub used to approve unconditionally, which hid that the Spam Log pill's Ham verdict on such a trashed comment put it back in the spam queue (`MarkCommentTest::test_a_ham_verdict_on_a_comment_trashed_from_the_spam_queue_does_not_restore_it_as_spam`; `BootstrapStubsTest::test_unspam_and_untrash_restore_the_recorded_status_like_core` pins the stubs). `get_comment()` consults a `$wp_comment_cache` global before the `$wp_comments` fixture — core reads the object cache ahead of the row, and WordPress's default cache is request-local, so an entry there is a snapshot another process has already superseded; nothing in the stubs populates it (a test seeds it to model that), `clean_comment_cache()` drops it, and `asw_test_set_comment_status()` calls that after writing, as core's `wp_update_comment()` does — which is what lets `ModerationTest` prove `ASW_Moderation::transition_is_current()` cleans the cache before it re-reads. `wp_die()` records `array( 'message', 'response' )` into the `$wp_died` global and then **throws** the named `ASW_Test_WP_Die_Exception` (named, so `expectException()` can address it), mirroring real WP's never-returns contract — a handler under test must be called inside try/catch. `check_admin_referer()` verifies `$_REQUEST[ $query_arg ]` against the existing `$wp_nonces` store and `wp_die()`s a 403 on a mismatch, and `wp_nonce_url()` appends the **unslashed** nonce read back out of that store. `is_feed()` is switchable via `$GLOBALS['wp_is_feed']` (default false), and `get_permalink()`/`home_url()` return `http://example.com/?p={id}` / `http://example.com{/path}`. `$wp_died` and `$wp_is_feed` are initialised once at bootstrap and must be reset per test; `tests/BootstrapStubsTest.php` pins all of it, because a stub that silently stopped firing the transition would make every moderation test pass vacuously. `wp_delete_file()` records every path it is given into the `$wp_deleted_files` global before delegating to `unlink()`, so `UninstallTest` can assert exactly which files the uninstaller removed. The `$wpdb` stub's generic `SELECT … FROM` branch honours a trailing `ORDER BY <col> [ASC|DESC]` (numeric values compared as numbers, everything else as strings), and `$wpdb->seed_table_rows( $table, $rows )` replaces a table's rows verbatim, ids included, and carries the auto-increment past every seeded id (as a real server's does, so a later `insert()` cannot hand back an id a seeded row already holds) — the pair exists because `insert()` only ever appends with an ascending auto-increment, so a table built through it comes back in id order whether the query asked for one or not, and `ASW_Sample_Repository::find_all()`'s `ORDER BY id ASC` could not be shown to do anything; `tests/BootstrapStubsTest.php` pins both, since a sorter that silently stopped sorting would make that assertion vacuous. `$GLOBALS['asw_zlib_unavailable']` (default false) makes `ASW_Model_Store::zlib_available()` report no zlib and `$GLOBALS['asw_gzcompress_fails']` (default false) makes `wrap_unit()` see a refused `gzcompress()`; both are read behind a `defined( 'ASW_TESTING' )` gate, because neither stored form's mismatch rules nor the cache-nothing rule is reachable on an image that has a working zlib. `$GLOBALS['asw_max_cached_unit_bytes']` (default null, leaving `ASW_Model_Store::MAX_CACHED_UNIT_BYTES` less its item-overhead allowance in force) is the third of these: it lowers the per-item limit `ASW_Model_Store::size_limit()` returns — verbatim, without that allowance — so `storable_unit()`'s prune-and-reweigh loop can be driven over an ordinary fixture instead of over megabytes of novel vocabulary, and `CorpusQualityTest::measure_units()` raises it to `PHP_INT_MAX` so the shipped-corpus size guard weighs the **unpruned** unit rather than asserting the write path's own postcondition. `$GLOBALS['asw_max_inflated_unit_bytes']` (default null, leaving `ASW_Model_Store::MAX_INFLATED_UNIT_BYTES` in force) is the fourth: it lowers the ceiling `inflate_ceiling()` returns, which is one value for two sides — what `inflate_unit()` hands `gzuncompress()` and what `storable_unit()` prunes against — because reaching 64 MiB honestly takes that much novel vocabulary. None of the four is reset by `reset_tables()` — `ModelStoreTest::setUp()`/`tearDown()` and `CorpusQualityTest::setUp()`/`tearDown()` reset them, and any other class that sets one must do the same. `asw_test_wrap_unit()` / `asw_test_unwrap_unit()` call `ASW_Model_Store::wrap_unit()` / `unwrap_for_read()` by reflection (`asw_test_model_store_call()`), so a test that seeds or reads a cached unit writes and reads whatever form this host writes and cannot drift from the stored format; `asw_test_wrap_unit()` returns **null** when the host cannot store a unit at all. `MultiLangCheckTest::test_long_single_word_is_classified_in_linear_time()` is the suite's only wall-clock assertion: it drives one 196 608-character word (three times `ASW_Detector::MAX_COMMENT_LENGTH`, with the sole Cyrillic character appended **last** so no short-circuit can hide the walk) through `check()` and requires it under 1.0 s. It is a complexity guard, not a benchmark — the old quadratic implementation took 6.4–10.9 s and the current one ~0.001 s, so the bound has roughly 1000x headroom; if it goes red the algorithm regressed, do not raise the bound. Its companions pin the verdicts the rewrite must not change: `test_long_single_script_word_is_not_flagged()` on the same long input, and the classification cases (`test_script_extensions_character_counts_as_one_script`, `test_combining_mark_ignored`, `test_non_ascii_digit_ignored`, `test_script_specific_punctuation_belongs_to_its_script`, `test_unlisted_scripts_share_the_other_bucket`, `test_listed_script_mixed_with_unlisted_script_flagged`, `test_unlisted_punctuation_and_symbols_are_not_a_bucket`, `test_invalid_utf8_does_not_disable_the_check`, `test_invalid_utf8_alone_is_not_flagged`) which are what keep `IGNORED_PATTERN`/`OTHER_PATTERN` and the malformed-UTF-8 sanitization from silently changing verdicts.

## Comment-query layer (`ASW_Shadow_Display`)

Added for the shadow-display work, which hooks `WP_Comment_Query` and the `get_comment` filter. All of them are pinned in `tests/BootstrapStubsTest.php`, and every switch below is put back to its default by `asw_test_reset_comment_query_stubs()`, which each test driving these stubs calls in `setUp()`/`tearDown()`.

- `apply_filters_ref_array()` / `do_action_ref_array()` — on the same `$wp_filters` / `$wp_actions` registries as `apply_filters()` / `do_action()`, in registration order, honouring `$accepted_args` (unlike the older two). A member passed as `&$this` stays a reference, which is how the query hands itself to `pre_get_comments`, `comments_clauses` and `the_comments` (`test_ref_array_hooks_hand_callbacks_the_reference_and_honour_accepted_args`, `test_comment_query_hands_callbacks_the_query_object_itself`).
- `wp_get_current_commenter()` — returns `comment_author` / `comment_author_email` / `comment_author_url` from `$GLOBALS['wp_current_commenter']` over empty defaults. `$GLOBALS['wp_current_commenter_throws']` makes it throw a `RuntimeException` whose message must never reach a log — the seam for `ASW_Shadow_Display`'s fail-open tests.
- `get_current_user_id()` / `is_user_logged_in()` on `$GLOBALS['wp_current_user_id']` (0 = logged out); `wp_doing_ajax()` / `wp_doing_cron()` on `$GLOBALS['wp_doing_ajax']` / `$GLOBALS['wp_doing_cron']` (default false). `is_admin()` still defaults to **true** (`$wp_is_admin`), so a front-end test must set `$GLOBALS['wp_is_admin'] = false` (`test_identity_stubs_follow_their_switches`).
- `get_comment()` accepts an object as well as an ID, as core does: an object is passed through as-is, an ID resolves cache-first (`$wp_comment_cache`, then `$wp_comments`) into a fresh object per call, and either way the result runs through `apply_filters( 'get_comment', … )`. It still never writes `$wp_comment_cache`, so a presentation-only filter can be proven to leave the cached row alone (`test_get_comment_applies_its_filter_and_passes_objects_through`).
- `$wpdb->comments` (`wp_comments`) exists so the shadow branch can bind it through `%i`.
- `wp_parse_list()` — core's body: a string split on commas and whitespace, an array's scalar entries.
- `WP_Comment_Query::$sql_clauses` and `$filtered_where_clause` are **protected**, as in core, so plugin code that reads them as public properties fails in the suite exactly as it does on a real site (`test_comment_query_internals_are_protected_as_in_core`). Tests reach them through `asw_test_get_sql_clauses( $query )` and `asw_test_set_approved_clause( $query, ?string )` (null removes the clause), both reflection-based.
- `WP_Comment_Query` — modelled on core's `get_comments()` order of operations over the `$wp_comments` fixture: `parse_query()` → `pre_get_comments` → cache key → (on a miss) `sql_clauses['where']` with `approved` first, built through `$wpdb->prepare()` with core's exact `( comment_author_email = %s AND comment_approved = '0' )` / `( user_id = %d AND comment_approved = '0' )` fragments → `comments_clauses` → row selection → `count` / `fields => 'ids'` shapes → `get_comment()` per ID → `the_comments` → `array_map( 'get_comment' )` → for a truthy `hierarchical`, one nested `WP_Comment_Query` per level with `parent__in` that keeps the parent's `fields` (so, as in core, each level is a full object query that runs `pre_get_comments` and `the_comments` — a plugin rule that skipped `fields => 'ids'` queries would otherwise silently lose every reply), with core's child-ID cache in front of it (`get_comment_child_ids:<parent>:<key>` in `$GLOBALS['wp_comment_query_cache']`, the key built from the vars limited to the keys of `query_var_defaults`; a cached level runs no nested query, so its comments pass through neither `pre_get_comments` nor `the_comments` — `test_a_cached_descendant_level_runs_no_nested_query`), then (for `'threaded'`) every comment re-fetched by ID through `get_comment()`, as core's `fill_descendants()` does; the result is returned flat, ordered by ID. `query_var_defaults` covers `post_id`, `status`, `include_unapproved`, `count`, `fields`, `parent`, `parent__in`, `hierarchical`, `number`, `offset`, `type` (`test_comment_query_runs_core_hook_order`, `test_include_unapproved_builds_core_approved_fragments`, `test_count_and_ids_queries_return_their_shapes`, `test_threaded_query_refetches_every_comment_through_get_comment` — the last also pins that `the_comments`' changes do not survive a threaded query, which is why the presentation needs a `get_comment` filter).
  - **Cache.** The key is `md5` of the query vars limited to the keys of `query_var_defaults`, minus `fields`. It is looked up in `$GLOBALS['wp_comment_query_cache']` (a miss stores the result, as core's `wp_cache_add()` does, and a hit skips the clauses and `comments_clauses` entirely), and every key used, hit or miss, is appended to `$GLOBALS['wp_comment_query_cache_keys']`. A var whose key is not in `query_var_defaults` does not reach the key (`test_cache_key_changes_when_a_query_var_default_is_added`).
  - **Log.** The final, post-filter WHERE of every query that missed the cache is appended to `$GLOBALS['wp_comment_query_log']`, so a test can assert it byte-identical.
  - **Matcher.** Post, parent, `parent__in` and type are applied from the query vars; the post-filter `sql_clauses['where']['approved']` is evaluated per row by a balanced-parenthesis OR/AND splitter that knows only core's shapes (`comment_approved = '…'`, `comment_author_email = '…'`, `user_id = N`, `comment_ID = N`) plus the plugin's shadow shape (`comment_type IN ( … )`, `comment_ID > N` and `EXISTS ( SELECT 1 FROM wp_commentmeta WHERE comment_id = wp_comments.comment_ID AND meta_key = '…' )`, true when the key is present in `$wp_comment_meta`). It throws `LogicException` on any other fragment, and when the final WHERE does not contain the post-filter approved clause — a filter that wrote the widened clause back without putting it into the WHERE (`test_matcher_throws_on_an_unknown_fragment`, `test_matcher_throws_when_the_where_and_the_approved_clause_disagree`, `test_matcher_evaluates_the_shadow_shape`).
- `wp_hash( $data, $scheme = 'auth' )` — core's body: `hash_hmac( 'md5', $data, wp_salt( $scheme ) )`, so the moderation hash a test computes is the one core would put into the redirect (`test_wp_hash_is_core_md5_hmac_keyed_with_the_salt`).
- `wp_get_unapproved_comment_author_email()` — core's body line for line, for the landing request after `comment_post_redirect`: a `$_GET['unapproved']` + `$_GET['moderation-hash']` pair resolves the named comment's `comment_author_email` (through `get_comment()`, so the `get_comment` filter runs) when `hash_equals( $_GET['moderation-hash'], wp_hash( comment_date_gmt ) )` holds and `time() < strtotime( comment_date_gmt . '+10 minutes' )`; otherwise it falls back to `wp_get_current_commenter()['comment_author_email']`, so `$GLOBALS['wp_current_commenter_throws']` reaches it too. The comment's status is never checked, as in core. There is no switch: a test drives the window through `comment_date_gmt` relative to `time()` and must reset `$_GET` itself (`test_unapproved_author_email_resolves_a_valid_pair`, `test_unapproved_author_email_falls_back_to_the_cookie` — wrong hash, expired window, unknown ID, missing argument —, `test_unapproved_author_email_falls_back_to_the_throwing_commenter`).
- `add_query_arg( $args, $url )` — follows core for a URL that already has a query string (parsed, an existing key replaced in place, new keys appended with `&`) and for a `#fragment` (split off first, re-attached last). A bare URL keeps the original `url?k=v` output, so existing callers' expectations are unchanged; values are still encoded through `http_build_query()`, unlike core's `build_query()` — the plugin only adds integers, slugs and hex hashes (`test_add_query_arg_keeps_the_existing_query_and_the_fragment`).
- `wp_parse_url( $url, $component )` / `wp_parse_str( $input, &$result )` — core's bodies for the absolute URLs `on_comment_post_redirect()` parses: `parse_url()`, and `parse_str()` of a string-cast input followed by the `wp_parse_str` filter (`test_wp_parse_url_and_wp_parse_str_read_a_redirect_query`).
