# Data storage

Reference moved out of `CLAUDE.md`. Where every piece of state lives, the duplicate-check transient map, the classifier cache layout and its fingerprints, the corpus quality floor and the measured sizes and timings.

Hybrid storage: seed training corpus in git-tracked `data/*.txt` files (read-only at runtime), user-added samples in DB table `{prefix}asw_samples` (written via admin AJAX from the Spam Log pill, and by `ASW_Moderation::on_transition()` on any comment status transition — which is **not** admin-gated and is reached from `admin-post.php` and from any front-end or cron moderation path, so `insert()` no longer has only `manage_options` callers). Settings, spam log, and stats stored in `wp_options`. 

Duplicate detection uses WordPress transients (`_transient_asw_dup_*`). Without an external object cache the transient is keyed **per hashed IP** (`'asw_dup_' . substr( hash( 'sha256', $ip_hash ), 0, 32 )`) and its value is a capped map of content hash => `{count, first_seen}` — so a sender posting unique texts adds no `wp_options` row per request, only entries inside the one row it already has. The map holds at most `ASW_Duplicate_Check::MAX_ENTRIES_PER_IP` (32) entries; a 33rd distinct text evicts the entry with the **lowest `count`**, ties broken by the oldest `first_seen` (first match wins on a further tie), and the trim runs on **every** write (not only when a new text arrives) as a `while` loop, so a map that somehow arrived oversized converges back to the bound instead of staying oversized for good — gating it on the new-hash branch left a sender who only ever repeats texts already in the map holding the oversized row forever, which is the one stream the convergence exists for. Evicting by count and not by age is load-bearing: `first_seen` is the window anchor and is never refreshed, so the oldest entry is by construction the *longest-tracked* text — the counter closest to the threshold — and age-based eviction discarded exactly what the check accumulates. Two streams reached it: a bot interleaving its repeated body with 32 unique fillers, and any shared `comment_author_IP` (a CDN that does not restore the real address, CGNAT, the CF7 `remote_ip` meta) where *other people's* ordinary comments evicted a spammer's count — on a busy shared IP the check was effectively off, silently, while the object-cache path still flagged the same input. Count-based eviction spends the *least* repeated slot instead, so ordinary single-shot traffic is what gets shed while a counter accumulates — it does not promise a repeated counter is never dropped: once every other slot holds a text repeated at least as often as the newcomer (a map wholly at count 2 or above) the minimum *is* a counter carrying a verdict, and it goes, because the entry being written is excluded from victim selection. That exception is not only the shared-IP accident it looks like — a sender can build the wall on purpose (32 texts sent twice each, 62 comments once the body under test is one of them) and then hold that body at count 1 indefinitely for **one** throwaway text per repeat, not the 32-per-repeat the filler wording below implies: the throwaway evicts the body, the body returns and evicts the throwaway, and the count-2 wall keeps those two the only spendable pair (`test_one_filler_per_repeat_holds_a_body_at_count_one_against_a_repeated_wall` pins it). Admitting the newcomer to victim selection — dropping it rather than a counter when it is the strict minimum — closes that and opens something strictly worse, which is why it is not done: the same wall would then refuse every new text outright, so a body repeated against it is never counted at all and the bypass costs nothing per repeat instead of one comment. Both residuals are inherent to a fixed bound; the shipped policy is the one that keeps the sender paying per spam comment. It closes those two streams **only from count 2 upward**, and the residual limit is not merely an evasion cost: a body never yet repeated is itself a count-1 entry, so more than 32 distinct texts *between every repeat* keep it at 1, and on a shared IP those 32 texts are other people's ordinary comments rather than anything the sender must send, so the flush costs the sender nothing. A repeat spaced by more than a full map's worth of unrelated traffic therefore still never accumulates on a busy shared IP, while the object-cache path (per IP + text) still flags it. That is inherent to any fixed bound — anything able to insert unlimited distinct keys flushes any bounded map — and is pinned as a known boundary by `test_a_never_repeated_body_can_be_flushed_by_fillers`, whose count-2 counterpart is `…_other_traffic_on_a_shared_ip_does_not_reset_a_duplicate_count`. The entry being written is excluded from victim selection for a load-bearing reason rather than a defensive one: with every slot held by a text repeated more often, a new text is the strict minimum and would evict *itself*, after which `increment_stored_count()` reads a missing key and returns null from an `: int` method — a `TypeError` swallowed by `ASW_Detector::run()`'s fail-open catch, silently disabling the check while appending a plugin-attributable line to the `debug.log` `dev/smoke.sh` scans (`test_a_new_text_survives_its_own_write_against_a_fully_repeated_map` pins it, and errors under a mutation that drops the exclusion). `test_repeated_text_outlives_a_seen_once_entry_on_eviction`, `…_repeats_interleaved_with_a_full_map_of_fillers_are_flagged` and `…_other_traffic_on_a_shared_ip_does_not_reset_a_duplicate_count` all go red if the policy reverts to age. The bound is what the fixed storage cost buys (32 × a 64-char hash plus two integers stays under a few kilobytes). Entries are validated and pruned on read: a non-array value yields an empty map, a top-level member that is not an array — which is what the bootstrap `set_transient()` stub's injected `__ttl` scalar is — or that lacks int `count` / int `first_seen` is skipped, each survivor is then rebuilt to exactly those two keys so a stored entry carrying extra members cannot smuggle them into the next write, and an entry older than the TTL is dropped — that per-entry drop *is* the window reset — as is one whose `first_seen` lies in the **future**, which a backwards clock step (an NTP correction, a VM resume) leaves behind and which no age test can ever expire: kept, it would count forever and, because the row's lifetime is derived from the newest `first_seen`, stretch the transient past `MAX_TTL` and immortalise every other counter in that IP's map (`test_a_future_dated_entry_is_dropped_and_does_not_extend_the_row` pins it), and the transient's own lifetime is recomputed from the newest entry's `first_seen` so it expires with its youngest window. The lock bucket (`substr( $transient_key, -2 )`, a bounded pool of 256 files) must stay derived from the **per-IP transient key**: that is what makes every writer of one IP's map take the same lock, the only thing serialising the whole-map read-modify-write. Deriving it from the content hash or the object cache's per-IP + text key would let two of one sender's requests interleave and each write back a map missing the other's increments. The no-`flock` fallback still writes unserialised, and since the value is now the whole map a lost update there costs that IP's other counters too, not just this text's — accepted, because a host without `flock()` must keep detecting rather than stop accepting comments. The lock is released in a `finally`, as every one of the plugin's fifteen lock sites is: the section calls `get_transient()`/`set_transient()`, so third-party `option_*`/`pre_transient_*` filters run inside it and can throw, and `ASW_Detector::run()` catches that and carries on — a release after the call would hold one hashed IP's exclusive lock (on a shared `comment_author_IP`, the whole site's) for the rest of the request. No unit test can reach that branch, so `PluginMetadataTest::test_every_exclusive_lock_is_released_in_a_finally_block()` pins it on the source text, per acquisition. The **external object cache path is deliberately left on per-IP + text integer counters** (`asw:asw_dup_…` keyed by `$ip_hash . $content_hash`) and is not converted to a read-modify-write map, because `wp_cache_incr` cannot update a list atomically; it keeps its existing fail-open behaviour: an eviction resets that pair's counter and starts a fresh `[now-window, now]` window from "now" rather than sliding the original `first_seen` anchor — the trade-off (a defender that can lose state under-counts rather than over-blocks) is documented inline in `class-duplicate-check.php`. 

Classifier state is cached as **one transient per writing system plus one combined unit**, written and read by `ASW_Model_Store` (never by `build_checks()`, which now loads nothing). Layout: a per-script unit is keyed `asw_classifiers_<script>` and holds `fingerprint`, `classifier` (Naive Bayes state, or `null` when that script has no samples at all) and `samples` (that script's pre-tokenised spam token lists for the Similarity check); the combined unit is keyed `asw_classifiers_combined` and holds `fingerprint`, `classifier`, `samples` and `has_script_samples`. Both members are stored **packed** — each sample's token list as one space-delimited string, each classifier category's `token_counts` as one interleaved `"token count token count …"` string, `token_totals`/`doc_counts` native — and **under an external object cache** the whole packed array is then **compressed** into the `zlib` envelope member, so what a cache item holds is `array( 'zlib' => gzcompress( serialize( $unit ), 6 ) )`; together with `ASW_Model_Store::LEARNED_SIMILARITY_BUDGET` those are what keep every unit inside the object cache's 1 048 576-byte per-item limit as the site learns. Without an external cache the transient is a `wp_options` row and holds the **plain** packed array: that column has no per-item limit, and `wpdb` refuses a deflate stream into it outright (`compression_applies()` in the `ASW_Model_Store` bullet). The store unpacks and inflates on restore, so `ASW_Naive_Bayes::set_state()` is unchanged; a unit cached in the pre-packing nested shape, and a stored form that does not match what this host writes, are each an unrecognised value that is deleted and rebuilt. A host without zlib — and every host without an external object cache — stores the plain packed array, which is exactly what the plugin stored before the envelope. The combined unit's `samples` member is the legacy corpus plus the `unknown`-script rows only (see the `ASW_Model_Store` bullet). `combined` is not a script-group name, so it cannot collide with a per-script key. The key names the unit and **never moves**; the invalidation fingerprint lives in the value, so a rebuild overwrites the unit it replaces — one row per unit, always — instead of orphaning it where no eraser could name it. **Every key must keep the literal `asw_classifiers_` prefix** (`ASW_Model_Store::TRANSIENT_PREFIX`): `uninstall.php` removes the cache with a `LIKE` over `_transient_asw_classifiers_%` / `_transient_timeout_asw_classifiers_%` and `tests/UninstallTest.php` asserts that `asw\_classifiers\_` pattern, so both stayed unchanged across this work — a unit key that dropped the prefix would leak past uninstall. 

There are four invalidation inputs, all of them folded into the unit's stored fingerprint rather than its key. A **per-script** unit's fingerprint is `filemtime:filesize` of `data/{spam,ham}-samples-<script>.txt` (`0:0` when the file is absent) + the excluded-tokens fingerprint + that script's DB fingerprint; the global sample revision is deliberately **absent**, so a training write under one script does not invalidate another's unit. The **combined** unit's fingerprint is all 22 files' `filemtime:filesize` + the excluded-tokens fingerprint + `dbrev:<latest_revision()>` **and** `dbtable:<ASW_Sample_Repository::table_fingerprint()>` (one prepared `SELECT COUNT(*) AS sample_count, MAX(id) AS max_id FROM %i`, folded as `<count>:<maxid>`, under the same `suppress_errors( true )` bracket and the same `last_error` failure test as `script_fingerprint()`, and omitted — leaving the revision alone, as this key carried before — when that read fails). The revision alone cannot carry the erasure race guard: `bump_revision()` is a *second* write, an `UPDATE` on `wp_options` fired after the `DELETE` it follows and unable to report a refusal, so an erasure whose bump the database refused removes rows while the revision stands still — and `combined_unit()`'s post-write supersession check, the thing that stops a request which loaded its samples before that erasure from writing them back after it, is built on the fingerprint moving when rows go. A component read from the table itself cannot be defeated that way (`ModelStoreTest::test_a_row_that_left_without_a_revision_bump_moves_the_combined_fingerprint` pins it); `COUNT(*)` moves when rows are erased and `MAX(id)` when rows are added, so an erasure followed by a fresh training insert is visible, exactly as per script. Per-script units need no such component — their DB fingerprint already reads the table. The **excluded-tokens fingerprint** (`md5( serialize( $excluded_tokens ) )`) is a new input: tokenisation moved off the request path into the cached unit, so a unit built under a different exclusion list must not be served. The **per-script DB fingerprint** is `ASW_Sample_Repository::script_fingerprint( $script )` — one prepared `SELECT category, COUNT(*) AS sample_count, MAX(id) AS max_id FROM %i WHERE script = %s GROUP BY category`, folded as `spam:<count>:<maxid>|ham:<count>:<maxid>` with `0:0` for a category with no rows. `MAX(id)` is what makes it exact: a privacy erasure followed by a new training insert leaves `COUNT` unchanged. The query runs inside a `$wpdb->suppress_errors( true )` bracket restored in a `finally`, exactly as `schema_is_current()` does and for the same reason — against a table that was never created the `SELECT` is a hard MySQL error and `wpdb::print_error()` writes it to `error_log()` regardless of `show_errors`, gated only by `suppress_errors`, so unbracketed it would append a plugin-attributable line to the very `debug.log` `dev/smoke.sh` scans on **every** submission rather than once per activation. Detecting that failure is **not** a return-value test: `wpdb::query()` calls `flush()` — which sets `last_result` to `array()` and clears `last_error` — before it runs, and on an error returns `false` without touching `last_result` again, so `wpdb::get_results()` hands back an **empty array**, byte-identical to what a script with no rows returns. `script_fingerprint()` therefore clears `$wpdb->last_error`, runs the query and treats a non-empty `last_error` as the failure (it is set regardless of `suppress_errors`, which gates only `print_error()`). Guarding on `! is_array( $rows )` alone was dead code on real WordPress: the method returned `spam:0:0|ham:0:0` on a refused read, which is exactly the fingerprint a privacy erasure of every row later produces — the same cache key, so the erased text would be served back out of the transient for up to 24 hours (`SampleRepositoryTest::test_script_fingerprint_tells_a_failed_read_apart_from_an_empty_script` pins the distinction). A **failed fingerprint read** makes the method return `null` — never a zero fingerprint, which would read as "no rows" — and the store substitutes `dbrev:<latest_revision()>` for that unit's DB component **and caches normally**. Not caching there is what must not happen: on the host whose samples table was never created — the refused-`CREATE` case the schema-version retry exists for — the query fails on *every* request, so a never-cache rule would put that site permanently on the cold path (~38 ms and ~11 MB per comment) where the old `latest_revision()` option read still cached; the global revision moves on every sample write, so invalidation stays correct, merely coarser. The **mid-load fingerprint race** — the fingerprint moving between the pre-load and post-load computation — is one of the two never-cache cases left. The other is a **failed sample read**: `ASW_Sample_Repository::find_all()` answers the empty array both for a script with no rows and for a `SELECT content` the database refused (`wpdb::query()` flushes `last_result` to `array()` before running and returns `false` without touching it again, so the `! is_array()` guard there is dead code on real WordPress, exactly as it was in `script_fingerprint()`), so a unit built through a refused read carries the corpus files alone while its fingerprint — computed from an aggregate query that *did* answer — asserts the rows are in it. Caching that would drop every user-added sample out of the Bayesian **and** Similarity models for the unit's whole day with no signal anywhere, and the branch widened the old exposure: the Similarity corpus used to be re-tokenised from `find_all()` on every request, so a transient failure cost one request, where it now poisons the cached unit. `find_all()` therefore sets a sticky `sample_read_failed()` flag (cleared by `clear_sample_read_failure()`, which `ASW_Model_Store` calls before loading a unit's samples) rather than changing its return type — many callers and tests depend on `array` — and both loaders check it **after** the build, since `build_combined_unit()` reads the `unknown`-script rows itself. The unit is still used for this request; it is only left uncached (`SampleRepositoryTest::test_find_all_reports_a_failed_read_through_the_flag_not_the_return_value`, `ModelStoreTest::test_a_script_unit_built_while_the_sample_read_failed_is_not_cached` and its `combined` twin pin it). That rule is **conditioned on the DB fingerprint component having been read successfully** (`unit_is_cacheable()`), because its whole premise is a fingerprint that asserts the rows are in the unit: when the aggregate read failed **as well** the component fell back to `dbrev:` and asserts nothing about them, and withholding the write is then the very thing the fallback exists to prevent — a samples table that was never created fails *both* queries on every request, so the two rules taken separately put that host on the cold path for every submission for good, which is strictly worse than the monolithic transient this store replaced. Caching on the fallback is safe because `dbrev:<n>` is a different string from `db:<fingerprint>`, so the first request whose read succeeds cannot match the unit and rebuilds it (`ModelStoreTest::test_a_host_whose_samples_table_is_missing_still_caches_its_units` and `…test_a_unit_cached_on_a_fallback_fingerprint_is_rebuilt_once_the_table_answers` pin both halves; the single-failure test above deliberately fails only the `SELECT content` query, so it does not cover this pair). `find_all()` carries the same `suppress_errors( true )`/`finally` bracket as `script_fingerprint()` and `table_fingerprint()` for the same reason — a cold combined-unit build calls it twenty times, and against a missing table each call would otherwise have `wpdb::print_error()` append a plugin-attributable line to the `debug.log` `dev/smoke.sh` scans. 

Bayesian seed data stored in `data/spam-samples.txt` and `data/ham-samples.txt` (legacy), plus per-script files `data/{spam,ham}-samples-{script}.txt` for 10 script groups. The seed corpus is comment spam — it is expected to transfer reasonably to Contact Form 7 submissions but this is unmeasured; a form-specific corpus is explicit future work and must not be introduced without a plan update. **The corpus is held to a quality floor, not just a line count.** The 1.0.0 release candidate shipped ~100 spam + ~100 ham one-line slogans per script, all 50–70 characters, one register ("Купите виагру дешево онлайн аптека…", "Отличная статья спасибо…"); the first real comment on antispamwizard.com — `продам гараж, пишите 89139991205` — passed every check, because the Bayesian check skipped it (32 characters against the then-default `min_message_length` of 50, a gate tuned to the corpus's own lengths rather than to spam) and, with the gate lowered, still scored 0.47: not one of its words existed in the corpus. The second live miss, `Зарубежный трафик нагон` — three words, none of them in the corpus, no phone, no link — showed that a hand-written ~400-line corpus is one genre short every time; the Cyrillic and Latin files were therefore rebuilt from a **genre matrix** (classified ads and "buying" ads, local services, construction, appliance and car services; traffic/leads/arbitrage, SEO, followers and reviews, advertising and mailing services, cheap web development and essays, software keys and cheats; earn-from-home, MLM, crypto, forex, investments, payout scams; loans, debt relief, casino, betting, coupons, phishing notices; pharmacy, weight loss, clinics, beauty, dating, folk cures; flattery-plus-own-site, documents and hacking, magic, courses, legal and migration, tours and delivery), each genre written as sixty-plus different spammers would phrase it, in many inflected forms (the classifier has no stemming) and in the secondary languages of each script (Ukrainian, Belarusian, Bulgarian, Serbian, Kazakh under Cyrillic; Spanish, German, French, Portuguese, Italian, Polish, Turkish, Indonesian, Vietnamese under Latin), with at least 40% of lines under 50 characters and most lines carrying no phone number or handle so the pitch words are learned, not just the phone marker. They now hold: latin 3795 spam / 5766 ham, cyrillic 3527 / 5046, cjk 4967 / 5393, arabic 3971 / 3954, devanagari 4020 / 4351, greek 3524 / 3520, hebrew 3976 / 4076, thai 5151 / 4987, bengali 4119 / 3445, indic 4302 / 4028. All ten were rebuilt from the same genre matrix — classified ads and "buying" ads, local services, construction, appliance and car services; traffic/leads/arbitrage, SEO, followers and reviews, advertising and mailing services, cheap web development and essays, software keys and cheats; earn-from-home, MLM, crypto, forex, investments, payout scams; loans, debt relief, casino, betting, coupons, phishing notices; pharmacy, weight loss, clinics, beauty, dating, folk cures; flattery-plus-own-site, documents and hacking, magic, courses, legal and migration, tours and delivery — each genre written as sixty-plus different spammers would phrase it, in that script's regional genres and secondary languages (Cyrillic: Ukrainian, Belarusian, Bulgarian, Serbian, Kazakh; Devanagari: Hindi plus Marathi and Nepali; indic: Tamil, Telugu, Kannada, Malayalam with smaller shares of Gujarati, Punjabi, Odia, Sinhala; CJK: Japanese kanji/hiragana/katakana plus Korean hangul/hanja; Arabic: Standard Arabic plus Persian and Urdu-influenced variants; Greek, Hebrew, Thai and Bengali in their own regional genres), with at least 40% of spam lines and 10% of ham lines under 50 characters and most lines carrying no phone number or handle so the pitch words are learned, not just the phone marker. Numbers that look like counts are kept in ham only when they cannot be mistaken for a phone number: no seven-or-more consecutive digits and no two digit groups separated only by spaces, because `ASW_Tokenizer::PHONE_PATTERN` folds both into `ASW_Tokenizer::PHONE_TOKEN` (`aswphonenumber`). The rule exists because digits were 9–38% of spam lines against 1–7% of ham, so a bare `100, 200, 300` body scored spam through the combined classifier — now the same body must route to ham. Two lessons from that rebuild are load-bearing for any further corpus edit. **Praise words are shared vocabulary**: the flattery genre opens with the same words ordinary readers use, and a block of 400 spam lines beginning `Great post, …` turned `Great post, thanks` and `Отличная статья` into 0.97 spam — the flattery block is therefore written as bare pitches (`check out my blog for more tips like this`) with only a minority carrying a varied prefix, and the ham files carry a praise block of their own. **Ham must cover the site's own vocabulary and its benign overlap with spam**: developer talk (`software architecture`, `design patterns`, `applications`), version numbers and counts (`PHP 8.1`, `WP 6.4`, `took 3 hours`), `Contact Form 7` (a body that ties Cyrillic and Latin letters routes to the **Latin** classifier, where `contact form` was pure spam from the mailing-services genre), `please check the typo`, and readers mentioning traffic, ads, subscribers, loans, casino, delivery, earnings in their own stories — without them the 1.0.0-style tests `test_legitimate_latin_comment_not_flagged` and `test_disabled_checks_do_not_trigger` went red on the Bayesian check alone. Note also that Laplace smoothing makes every *unknown* word lean toward the category with **fewer total tokens**, so the two categories are kept within ~15% of each other in token count; when they drift apart, all-unknown comments drift with them. Measured over the shipped corpus via `ASW_Tokenizer::tokenize_for_script()` with **no excluded tokens** (the count `dev/corpus-eval.php` and the test share; with the default excluded-token list the Cyrillic and Latin ratios come out lower, 1.22 and 1.27) the ham/spam token ratios are cjk 1.063, thai 1.052, arabic 1.048, devanagari 1.104, bengali 0.895, indic 1.017, greek 1.154, hebrew 0.968 — all inside the 0.85–1.20 band that `CorpusQualityTest::test_corpus_token_counts_stay_balanced_between_categories()` enforces — with cyrillic 1.254 and latin 1.377 as the standing exempt pair that drifted before this work. Held-out fixtures (50 spam / 50 ham per script) at the shipped `bayesian_threshold` 0.70 give latin 1.00 recall / 0.00 FPR, cyrillic 1.00 / 0.00, cjk 1.00 / 0.00, arabic 1.00 / 0.00, devanagari 1.00 / 0.00, greek 1.00 / 0.00, hebrew 1.00 / 0.00, thai 0.96 / 0.00 (2 misses), bengali 0.98 / 0.00 (1 miss), indic 1.00 / 0.00; 5-fold CV on the corpus itself gives latin 0.88/0.03, cyrillic 0.91/0.02, cjk 0.91/0.04, arabic 0.92/0.01, devanagari 0.91/0.03, greek 0.88/0.03, hebrew 0.91/0.02, thai 0.82/0.06, bengali 0.94/0.04, indic 0.93/0.04. `CorpusQualityTest` now gates all ten scripts (SCRIPTS = latin, cyrillic, cjk, arabic, devanagari, greek, hebrew, thai, bengali, indic) with per-script canaries (four spam — classified ad with phone, traffic/leads pitch, visit-my-site, region-specific genre — and four ham — thank-you, typo report, version/count, benign spam-adjacent story — each 15–80 chars, all inside `CANARIES`/`HAM_CANARIES`) and `dev/corpus-eval.php` prints the per-script token line (`tokens: <spam> spam / <ham> ham, ham/spam <ratio>`) after the held-out block. 

The cost of the larger corpus **was** memory, and `ASW_Model_Store` is what paid it down: a warm `build_checks()` used to unserialise a ~2.4 MB transient holding every script's classifier **state only** — loaded on every submission regardless of the comment's script — and then **re-tokenise every script's spam corpus from the files on every request** for the Similarity check, which the old transient never cached; together that peaked ~26 MB above baseline in ~43 ms, and the cold rebuild ~35 MB in ~193 ms. Caching the pre-tokenised Similarity corpus alongside the classifier state is therefore **new** in this change, and is why a unit is larger than its share of the old transient (the tokenised corpus is the bigger half of every unit). Measured on the `asw-site` stack (`wordpress:7.1-php8.3-apache`, PHP 8.3) with `dev/bench.php`, 5 runs per case over a 285-character Cyrillic spam body: `build_checks()` is **0.01–0.03 ms / 0.03 MB** cold *and* warm, because it loads nothing; a **warm** build plus one `ASW_Detector::evaluate()` is **2.95 ms / 4.73 MB** (was 45.7–47.6 ms / 26.18 MB before the store); the **one-script cold path** — the first submission after a cache flush, which is where the cold cost moved — is **37–48 ms / 8–11 MB for most writing systems** (e.g. latin 30.8 ms / 6.22 MB, cyrillic 37.3 ms / 9.08 MB, arabic 41.2 ms / 10.5 MB, devanagari 48.2 ms / 11.0 MB, greek 35.8 ms / 8.62 MB, hebrew 42.0 ms / 10.80 MB, bengali 42.0 ms / 10.93 MB, indic 47.4 ms / 15.11 MB), **up to 129 ms / 34 MB for cjk (128.98 ms / 34.39 MB) and 206 ms / 35.9 MB for thai**, where the corpus is largest; and the **`unknown`-script cold path**, the only one that builds the combined unit, is **~553–566 ms / 30.5 MB** (was 190.41 ms / 31.53 MB). The warm figure is the one **regression** in the set and is reported as such: **+0.3 ms per submission**, the cost of unpacking the packed `token_counts` and sample lists on restore. The learned-sample budget and the compressed envelope cost this stack nothing measurable: it runs without an external object cache, so its units are the plain packed arrays they already were (the re-measurement after the envelope was confined to the cache is within run-to-run noise of the pre-branch 2.68 / 32.18 / 97.84 ms). `peak alloc` (`memory_get_peak_usage( false )`) is the comparable column throughout; `peak real` is the arena PHP holds from the OS, so a warm run allocating inside what an earlier cold run already grew reads as 0. `dev/bench.php` (`wp eval-file`, no `declare( strict_types=1 )` — `eval-file` runs through `eval()`, where a `declare()` can never be the first statement, the rule `detect.php` and `waitlist.php` already follow, and `PluginMetadataTest` now asserts for all three) re-measures it over five cases — cold and warm `build_checks()`, warm and cold `build_checks()` + one `evaluate()` for the Cyrillic body, and a cold one for an `unknown`-script body, which is the only case that builds the combined unit — then evaluates both bodies once more (every measured case flushes, so only the last one's unit would otherwise still be on disk) and prints two sizes for every `asw_classifiers_*` unit it finds: the `wp_options` **row** (the plain packed unit, which is what this stack stores and which has no per-item limit) and what an object cache would be handed for the same unit (`serialize( array( 'zlib' => gzcompress( …, 6 ) ) )`), which is the number checked against 1 048 576 and printed with the ratio between the two, so a future corpus edit can see whether more corpus or worse-compressing content moved it. Over the two units a Cyrillic and an `unknown`-script body build, that is combined 1 058 191 B row / **468 454 B cached** (44.7% of the bound, 2.26x) and cyrillic 664 818 / **187 174** (17.9%, 3.55x) — the same numbers `CorpusQualityTest` measures in the suite. 

**Size budget: every unit is under the 1 048 576-byte object-cache item limit, and this now holds by construction as the site learns rather than by one-off measurement.** Four measures together make it hold, all four in `ASW_Model_Store`: the **packed** representation above; a **compressed** stored form under an external object cache, `array( 'zlib' => gzcompress( serialize( $unit ), 6 ) )`, which is what the cache item actually contains and therefore the only size the limit applies to (a `wp_options` row holds the plain packed array and has no per-item limit); `LEARNED_SIMILARITY_BUDGET = 131072`, the packed bytes of *learned* spam a unit's similarity corpus may carry, spent from the newest sample downwards; and — because the classifier's *bytes* are a function of what the site has learned and no budget can predict them — `storable_unit()`, which weighs the value it is about to write against `MAX_CACHED_UNIT_BYTES` and, while it is over, drops the least frequent half of each category's vocabulary and weighs it again, handing the pruned model back to the live classifier so the request that built the unit scores exactly as every warm one after it does. That last one runs only under an external object cache, which is the only backend with a per-item limit. See the `ASW_Model_Store` bullet for the envelope, the strict-on-serve / lenient-on-erasure read split, the no-zlib fallback, the budget's arithmetic, the verdict change it costs the Similarity check, and the admission control with the alternatives measured against it. Measured over the shipped corpus on the test image — as a cache item, which is where the bound applies: cjk **768 654 B stored** (73.4% of the 1 047 552-byte pruning bound; 2 150 316 uncompressed, 2.80x) has the least headroom, followed by combined 468 454 (44.7%; 1 058 191, 2.26x), indic 294 280 (28.1%; 1 277 901, 4.34x), thai 277 950 (26.5%; 2 188 690, 7.87x — the best-compressing unit), arabic 215 900 (20.6%; 731 446, 3.39x), hebrew 207 514 (19.8%; 740 295, 3.57x), devanagari 200 140 (19.1%; 869 242, 4.34x), cyrillic 187 174 (17.9%; 664 818, 3.55x), bengali 185 398 (17.7%; 867 498, 4.68x), greek 167 225 (16.0%; 634 017, 3.79x), latin 141 551 (13.5%; 357 500, 2.53x) — **2 932 240 bytes stored for all eleven** against 10 837 954 uncompressed. Every unit is under the pruning bound by construction, and cjk leaves the least margin; a cjk site's learned dictionary is therefore the first to be pruned by `ASW_Model_Store::storable_unit()` while the budget still fits (cjk stored 768 654 + `LEARNED_SIMILARITY_BUDGET` 131 072 = 899 726 < 1 047 552). Two were over the bound before the packed representation and the narrowed combined corpus — the Cyrillic unit at 1 050 388 bytes and the **combined** unit at 3 284 015, the latter larger than the whole 2 455 017-byte monolithic transient it replaced. The corpus is not the only input, and the second one is **unbounded on the site's side**: a unit is the corpus plus every training sample the site has added (`ASW_Training_Data::load_script_samples()` merges `ASW_Sample_Repository::find_all()` in), so a script's learned samples grow that script's unit and the combined unit trains on all of them — the independence above is from another script's *corpus*, not from a script's own learned samples. That was an open finding until this change: 400 learned 40-word novel-vocabulary Cyrillic samples took the cyrillic unit to 1 173 708 bytes and a comment is bounded only by `ASW_Detector::MAX_COMMENT_LENGTH`, so nothing in the plugin stopped a unit crossing the limit, after which a persistent object cache refused the write silently and every submission routed to that unit paid a cold rebuild for good (absent entirely without an external object cache, where a transient is a `longtext` option row with no per-item limit). The budget and the envelope close it, and three tests pin the result. `CorpusQualityTest::test_every_cached_model_unit_fits_the_object_cache_item_limit()` is the standing corpus guard — it builds all eleven units over the **shipped corpus** through a real `ASW_Model_Store` (no repository) and fails on any whose **stored, compressed** payload reaches 1 047 552 bytes, printing every unit's stored and uncompressed size, so a corpus edit that breaks the budget goes red in `docker compose run --rm test` rather than waiting for a hand-run benchmark. That figure — and `bench.php`'s — is `MAX_CACHED_UNIT_BYTES` less `CACHE_ITEM_OVERHEAD_BYTES`, i.e. the limit production actually prunes at, which is why that constant is public: flagging at the raw 1 048 576 left a kilobyte-wide band in which a unit passed both guards and was still pruned on a live site. `…test_an_unbounded_learning_history_still_fits_every_unit()` replaced the old headroom test and drives a history past **both** bounds at once: 1 300 learned Cyrillic `spam` samples of 40 words of entirely novel vocabulary (pessimistic per *token* — a real learned comment reuses the corpus's words — and the heavier category, since a spam sample enters the script unit's similarity corpus as well as its classifier) leave cyrillic at 533 375 B stored (50.9%; 1 518 153 uncompressed) and combined at 469 322 (44.8%). Its anti-vacuity guards are the point of it: every insert must land, all 52 000 tokens must be unique and absent from the shipped corpus (drawn by a *local* seeded LCG — never `mt_srand()`, which would perturb the process-global sequence every later test draws from — with each candidate rejected unless it is both unseen and untokenised out of any `data/*.txt` file, so "pessimistic per token" is enforced by construction and cannot decay as the corpus grows into the space those words are drawn from), the samples must really have reached the cyrillic **and** combined units (a store handed a repository but a repositoryless `ASW_Training_Data` builds byte-identical units), the spam dictionary must really have reached `ASW_Naive_Bayes::MAX_DICTIONARY_SIZE`, and the learned half of the similarity corpus must really have been **truncated** — it comes to 130 784 bytes in 218 of the 1 300 samples, under the budget and short of the history, so the test cannot pass because the cap silently did nothing. `…test_a_full_dictionary_worst_case_unit_fits_the_object_cache_item_limit()` is the plan's arithmetic as an executable assertion: a synthetic 50 000-token-per-category dictionary, the whole shipped Cyrillic similarity corpus and a full `LEARNED_SIMILARITY_BUDGET` of learned lists, packed and compressed through the store's own packers **by reflection** so the measurement cannot drift from the stored format, come to **874 205 bytes stored** (83.4%; 2 213 777 uncompressed), 174 371 bytes under the limit. `bench.php` flags any unit past the same pruning bound by exact byte count as well, against the **stored** size and with the uncompressed size and the ratio printed alongside so a future corpus edit can see which half moved — more corpus (the uncompressed column grows) or worse-compressing content (the ratio moves). Its case (e) exists so the combined unit is actually built before the sizes are read: a Cyrillic body never loads it, so a Cyrillic-only benchmark reported on the units that are *not* the worst one (and the benchmark builds only the two units its own bodies reach, so recording the full set means building every unit in one pass). The per-script units are **independent** — a unit's fingerprint and contents are that script's alone — so growing another script's corpus cannot enlarge them; the growth axis the *corpus* has left is the **combined unit's classifier state**, nearly all of its 765 095 uncompressed bytes, because it trains on every script's samples. Any future corpus ticket must therefore re-measure the combined unit, and note that packing the classifier state is not optional for it: unpacked, that state alone serialises to 1 225 068 bytes, i.e. over the limit even with every sample list removed. Getting under the bound also retired the core deprecation this cache used to provoke: with `debug.log` truncated to 0 bytes and all eleven units flushed, one Cyrillic and one `unknown`-script `evaluate()` each wrote their unit and left `debug.log` at **0 bytes** — no `preg_replace(): Passing null to parameter #3 ($subject) is deprecated` from `wp-includes/class-wpdb.php`, because the packed `INSERT` no longer overruns PCRE's backtrack limit in `wpdb::get_table_from_query()`. `dev/smoke.sh` and `site/verify.sh` both scan `debug.log` and both pass. 

`min_message_length` defaults to 10. `tests/CorpusQualityTest.php` pins it: for all ten scripts it trains the real per-script classifiers from the shipped files and requires recall ≥ 0.90 on the held-out spam and a false-positive rate ≤ 0.04 on the held-out ham in `tests/fixtures/corpus/{spam,ham}-{script}.txt` (50 lines each, written separately from the corpus and asserted never to be copied into it), that the short-spam canaries (the garage ad among them, one phone digit off the fixture line it also is, since no canary may equal a corpus or fixture line) are flagged and the short-ham canaries are not through the real `ASW_Bayesian_Check` at the shipped defaults, that at least a third of each spam file and a tenth of each ham file is under 50 characters, and — for all ten scripts — that no line is duplicated or present in both categories. `dev/corpus-eval.php` (`docker compose run --rm test php dev/corpus-eval.php [script …] [-v]`) prints the same held-out numbers plus a 5-fold cross-validation per script, listing misses and false positives; run it after any corpus edit. Cross-validation on a homogeneous corpus is flattering (the old files scored 0.95+ against themselves), which is why the held-out fixtures, not the CV, are what the test enforces. 

`uninstall.php` removes all stored data (options, transients, comment meta, DB table, lock files) — update it when adding new storage locations. Personal data (the spam-log fragment + SHA-256 IP hash, keyed by `comment_id`, and the `_asw_reason` comment meta) is also exportable and erasable per data subject via the WordPress Privacy API — see `ASW_Privacy`; additionally the Contact Form 7 integration stores flagged form submissions in the same `asw_spam_log` option with `source => 'form'` and a salted SHA-256 `email_hash` (via `ASW_Detector::hash_email()`, never the raw email) so the Privacy API can reach them by hash on page 1 via `get_entries_by_email_hash()` / `delete_entries_by_email_hash()` — no new storage location is introduced, so `uninstall.php` is unaffected. User-added training samples are personal data too — they hold the trained comment's full text — and are keyed by a required non-zero `comment_id` plus a secondary salted `email_hash`, so they are export- and erase-covered both by the same subject lookup (`find_by_comment_ids()` / `delete_by_comment_ids()`) and, once the source comment has been hard-deleted, by hash (`find_by_email_hash()` / `delete_by_email_hash()`); the hash is the existing `ASW_Detector::hash_email()` value, so no new *kind* of data is stored; `uninstall.php` deletes the table whole, so the subject key itself adds no storage location — but the schema-version option `asw_samples_db_version` does, and `uninstall.php` removes it alongside `asw_samples_revision` (`tests/UninstallTest.php` asserts both). `uninstall.php` is no longer required to stay byte-identical (it uses `wp_delete_file()` and annotated `DirectDatabaseQuery` suppressions as of the Plugin Check work; the `%i` identifier-placeholder conversion applies to `ASW_Sample_Repository` and `ASW_Model_Store::delete_unit_rows()`, not the uninstaller); the baseline is now behavioural — **the removed data set must stay exactly identical**, asserted by `tests/UninstallTest.php` (options, transients, `_asw_reason` comment meta, `DROP TABLE`, and every file inside the runtime `.asw-locks` directory including its `index.php`/`.htaccess` guards, plus the now-empty directory itself). The shipped `data/` directory carries no `.htaccess`; `antispam-wizard/data/index.php` (`// Silence is golden.`) is the guard that keeps the corpus unlistable, and `tests/PluginMetadataTest.php` asserts both facts. Dropping the `.htaccess` is a deliberate downgrade — it carried `Deny from all`, whereas `index.php` only prevents directory listing, so the individual `data/*.txt` corpus files are now directly fetchable by URL. That is accepted because WordPress.org rejects hidden files in the shipped tree and the corpus is public, GPL-shipped, non-personal data that ships inside the plugin zip regardless. The bot checks (Honeypot, Submit Time) do not persist any data; since no new storage location is introduced by them, `uninstall.php` and `ASW_Privacy` are unaffected.
