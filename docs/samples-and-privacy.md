# Spam Log, Sample Repository and Privacy

Reference moved out of `CLAUDE.md`. The three classes that store, key and erase per-subject data: `ANTISPAMWIZARD_Spam_Log` (training claims), `ANTISPAMWIZARD_Sample_Repository` (schema, subject keys, versioned DDL) and `ANTISPAMWIZARD_Privacy` (exporter/eraser).

## `ANTISPAMWIZARD_Spam_Log`

FIFO log (max 100 entries) with file locking; invalidates the `antispamwizard_spam_log` option cache (`wp_cache_delete`) on every access path — both read paths (`get_entries()`, `is_trained()`) and mutating paths (`add_entry()`, `mark_trained()`, `clear()`, `claim_training()`, `restore_training()`) — so a stale persistent object cache can never serve an outdated log. `claim_training( $comment_id, $category )` is the atomic once-per-comment-and-category training claim `ANTISPAMWIZARD_Moderation` is built on: it reads and writes `trained_as` inside one `flock` bracket and returns `'ok'` (was untrained, now `$category`), `'flipped'` (carried the other category, now `$category` — with exactly two categories that return value *is* the previous value, so the caller needs no second read), `'already_trained'` (already `$category`; nothing written, and the option stays byte-identical) , `'not_found'` (no entry for this comment) or `'failed'` — an entry was found but the `update_option()` that would have claimed it was **refused**; the value handed to it always differs from the stored one, so a `false` there is a failed write and not the no-change case. `'failed'` is deliberately *not* collapsed into `'not_found'`: that value means "no entry exists", which `ANTISPAMWIZARD_Moderation` answers by training **unlocked**, and doing that on a refused flip would insert the new category and delete the old one while the entry on disk still names the old one — after which every later transition back reads `'already_trained'` and stores nothing, making the disagreement permanent. Nothing was written, so there is nothing to roll back either; the caller returns and the next moderation retries (`SpamLogTest::test_claim_training_reports_failed_rather_than_not_found_on_a_refused_flip` and `ModerationTest::test_a_refused_flip_claim_does_not_move_the_table_under_the_stored_category` pin it). `restore_training( $comment_id, $category )` is its rollback counterpart and writes `trained_as` **unconditionally**, unlike `mark_trained()`, which refuses to overwrite. It and `unmark_trained()` return **`bool`** rather than `void`: a rollback write that is refused leaves the claim standing over a training that never happened, which every later transition then reads as `'already_trained'`, so the loss is permanent and invisible — `ANTISPAMWIZARD_Moderation::roll_back_claim()` logs a sanitized diagnostic naming the comment. "Nothing to write" is not a failure in either method (an entry already carrying the value, an entry carrying no mark, or no entry at all all return true), so `update_option()`'s no-change `false` is never reported as a refused write. `mark_trained()`/`is_trained()` are untouched and `unmark_trained()`'s behaviour is unchanged, so `ANTISPAMWIZARD_Admin_Page::ajax_mark_comment()` still claims through `mark_trained()` and still refuses a flip on the log entry

## `ANTISPAMWIZARD_Sample_Repository`

DB-backed storage for user-added training samples in `{prefix}antispamwizard_samples` table; content deduplication via SHA-256 hash; atomic revision counter in `wp_option 'antispamwizard_samples_revision'` for cache invalidation. Every sample carries a required non-zero `comment_id` subject key (column + `KEY idx_comment_id`): `insert( $script, $category, $content, $comment_id, $email_hash = '' )` returns `false` and writes nothing when `$comment_id <= 0`, so an unattributed sample — one the Privacy API could neither export nor erase — cannot exist at runtime. It also carries a **secondary** subject key, `email_hash` (column + `KEY idx_email_hash`), the same salted SHA-256 `ANTISPAMWIZARD_Detector::hash_email()` value the form spam-log entries use — never the raw address, `''` when the comment had no author email. It is load-bearing rather than redundant: `comment_id` only resolves for as long as the comment exists, and emptying the spam queue hard-deletes exactly the comments samples are trained from, after which the full comment text would live on in the table undiscoverable by an export or erasure request while `readme.txt` and the suggested policy text promise it is reachable. Dedup stays on the text, so training a second comment with identical text keeps the first row and the first comment's `comment_id` and `email_hash` (accepted edge case, documented on the unique key). `find_by_comment_ids()` (ordered by `id`, so an export is deterministic) / `delete_by_comment_ids()` and `find_by_email_hash()` / `delete_by_email_hash()` are the Privacy API's fetch/erase paths; `find_all( $script, $category )` is `ORDER BY id ASC`, and that clause is contractual rather than cosmetic: `ANTISPAMWIZARD_Model_Store::admit_within_budget()` spends `LEARNED_SIMILARITY_BUDGET` from the newest end of that list, and the autoincrement is the only column that can define “newest” — `created_at` is second-granular, so a moderation batch ties, and it does not track re-insertion either (`SampleRepositoryTest::test_find_all_returns_samples_in_ascending_id_order` pins it against rows seeded out of id order, through the `$wpdb` stub's `seed_table_rows()`). `find_categories_by_hash( $script, $hash )` is the read-side counterpart of `insert()`/`delete_by_hash()` — one query naming which categories a given sample identity is stored under, the only correct way to ask "is this text already trained, or trained as both?", since the content dedup keeps just the first comment's `comment_id` on a shared row (`ANTISPAMWIZARD_Moderation::training_is_settled()` is its caller); a delete that actually removed rows calls `bump_revision()`, so the cached classifier is rebuilt without the erased text. Both deleters return **`int|false`, not `int`** — `false` means the DELETE failed, which the eraser must report as `items_retained`, never collapse into the `0` of "nothing matched" (`SampleRepositoryTest::test_delete_by_comment_ids_returns_false_and_keeps_rows_when_the_query_fails` and its `…email_hash…` twin pin it). An empty `$email_hash` matches nothing in either method and issues no query at all: `''` is what every sample from an address-less comment stores, so a hash lookup on it would match them all. The DDL carries a schema version (`DB_VERSION` — `'1'` is the layout 1.0.0 ships — recorded in `DB_VERSION_OPTION = 'antispamwizard_samples_db_version'`, the `DB_VERSION` pattern of the site repository's waitlist store): `ANTISPAMWIZARD::activate()` writes it after `dbDelta()`, and `ANTISPAMWIZARD::maybe_upgrade_schema()` — hooked on `admin_init` from `init()` — re-runs `dbDelta()` and rewrites the option whenever the stored version differs. This is load-bearing: `register_activation_hook` does **not** fire on a plugin update, so without it a site that already had the table would keep an older layout and every `insert()` would fail with `Unknown column`, permanently breaking training. Both writers stamp the option **only after `schema_is_current()` confirms the DDL landed** — `dbDelta()` builds its return value from the diff it *intends* to apply and fires each `CREATE`/`ALTER` through `$wpdb->query()` without checking the result, so a statement the database refused (no `ALTER` privilege, a metadata lock, a full disk) is indistinguishable from a success; stamping unconditionally would turn a transient refusal into permanent breakage by short-circuiting every later attempt, which is the exact failure the version option exists to prevent. Leaving the option behind makes the next `admin_init` retry (`AntiSpamWizardTest::test_maybe_upgrade_schema_does_not_record_the_version_when_the_ddl_failed`, `…_retries_after_a_failed_ddl` and `test_activate_does_not_record_the_version_when_the_ddl_failed` pin it). That deliberate retry is why `maybe_upgrade_schema()` gates itself on `current_user_can( 'manage_options' )`: `admin_init` is **not** an admin-only hook — `wp-admin/admin-ajax.php` and `wp-admin/admin-post.php` both `do_action( 'admin_init' )` *before* their `is_user_logged_in()` check, so an unauthenticated request reaches the handler, and on a site whose `ALTER` the database keeps refusing every anonymous hit would re-run a full `dbDelta()` plus the `SHOW COLUMNS` probe — an unauthenticated database-load amplifier. `manage_options` rather than `wp_doing_ajax()` because it covers `admin-post.php` too, holds on multisite subsites where `activate_plugins` does not, and is already the capability of `ANTISPAMWIZARD_Admin_Page::ajax_mark_comment()`, the only caller of `insert()` — so the migration still always runs before anything can depend on the new column (`test_maybe_upgrade_schema_is_skipped_without_the_manage_options_capability` and `…_runs_for_a_capable_user_after_an_anonymous_request` pin both halves). `schema_is_current()` probes every entry of `VERSIONED_COLUMNS` with `SHOW COLUMNS FROM %i LIKE %s` (the column name through `esc_like()`, since `_` is a LIKE wildcard) **and** every entry of `VERSIONED_INDEXES` with `SHOW INDEX FROM %i WHERE Key_name = %s` (`SHOW INDEX` has no `LIKE` form). Both probes run inside a `$wpdb->suppress_errors( true )` bracket restored in a `finally`: against a table that does not exist either statement is a hard MySQL error, and `wpdb::print_error()` writes `WordPress database error … doesn't exist` to `error_log()` regardless of `show_errors` — gated only by `suppress_errors` — so on a host whose DB user cannot `CREATE` the table, `activate()`'s probe (fired straight after `dbDelta()`) would emit unexpected output during activation and every later capable `admin_init` would append a plugin-attributable line to the very `debug.log` `dev/smoke.sh` scans. A *missing column or index* needs no suppression: those return an empty result set, not an error. `SampleRepositoryTest::test_schema_probes_run_with_wpdb_errors_suppressed` pins the bracket and the restore. Probing the indexes as well as the columns is not belt-and-braces: `dbDelta()` emits the `ADD COLUMN` and the `ADD KEY` as separate `ALTER`s and checks neither result, so a database that accepted one and refused the other looks identical to a complete migration — stamping the version on the column alone would leave the index missing for good, because the version gate then short-circuits every later attempt (`AntiSpamWizardTest::test_maybe_upgrade_schema_does_not_record_the_version_when_only_the_index_ddl_failed` pins it). Bump `DB_VERSION` and extend both lists on any future DDL change; `SampleRepositoryTest::test_versioned_schema_probes_cover_every_key_the_ddl_adds` fails if a column *or* an index is added to the DDL without being probed — it diffs both the DDL's named indexes and its column names against the two lists, allowing only the columns and the dedup index of the original `CREATE`, which exist on every table the plugin ever created. Rows that predate the two subject keys get their defaults (`comment_id = 0`, `email_hash = ''`), which neither Privacy API lookup can match — `normalize_comment_ids()` drops non-positive IDs and both hash methods refuse `''` — so such a row would hold the trained comment's full text permanently beyond the reach of an export or an erasure request that `readme.txt` and the suggested policy text promise reaches it. Both schema writers therefore call `delete_unattributed()` (`DELETE … WHERE comment_id = 0 AND email_hash = ''`, `bump_revision()` when it removed rows) **before** stamping the version, and treat its `false` exactly like a refused `ALTER`: leave the version behind and retry next request. It runs from `activate()` as well as `maybe_upgrade_schema()` because reactivating after an in-place update stamps the version from `activate()`, which would otherwise strand those rows for good; on a fresh install it is a no-op against an empty table. `AntiSpamWizardTest::test_maybe_upgrade_schema_drops_samples_no_subject_key_can_reach`, `…_when_the_purge_failed` and their `activate` twins pin it, and `dev/smoke.sh`'s SCHEMA assertion covers it end to end: it seeds a row, rolls the live table back to a pre-release layout (both columns and both indexes dropped — the only place the real `ADD COLUMN comment_id … NOT NULL` against a *populated* table is exercised), runs `maybe_upgrade_schema()` and asserts the seeded row is gone

## `ANTISPAMWIZARD_Privacy`

WordPress Privacy API integration (GDPR Art. 13/15/17). Registers a personal-data exporter and eraser (`wp_privacy_personal_data_exporters` / `_erasers`) and suggested privacy-policy text (`wp_add_privacy_policy_content` on `admin_init`). Plugin data is keyed by `comment_id`: given the subject's email, WP core finds the matching comments (`get_comments` queried with `status => 'any'` so spam-/trash-queued comments — where the plugin's data actually lives, since detection stores flagged comments as `comment_approved = 'spam'` — are not excluded by the default `all` status) and this class exports/erases the corresponding spam-log entries (via `ANTISPAMWIZARD_Spam_Log::get_entries_by_comment_ids()` / `delete_entries_by_comment_ids()`) and the `_antispamwizard_reason` comment meta. Additionally, form entries logged with `source => 'form'` and `email_hash` are reached on page 1 via `ANTISPAMWIZARD_Spam_Log::get_entries_by_email_hash(ANTISPAMWIZARD_Detector::hash_email($email))` / `delete_entries_by_email_hash()` (case/whitespace-insensitive, never matching comment entries), emitting `antispam-wizard-form-<entry_id>` groups with date flagged, submission fragment, IP hash and triggered checks. Training samples added from the subject's comments are covered by **both** keys: `export()` emits one `antispam-wizard-sample-<sample id>` item per row returned by `ANTISPAMWIZARD_Sample_Repository::find_by_comment_ids()` (every page) **and** `find_by_email_hash()` (page 1 only, like the form entries — hash-keyed rows do not paginate), merged into one array keyed by row `id`. The two keys paginate differently — the hash query runs on page 1 while the row's comment may fall on page 3 — and the row index collapses a duplicate *within* a page but never *across* pages, so a subject with more than 50 comments would otherwise export a sample trained from a comment on page 2 twice, and WordPress merges groups sharing an `item_id`, showing up as the full comment text repeated inside one item. The split is therefore decided **per row, from facts that do not depend on what another page's queries returned**: the comment-keyed pass is never skipped, and the hash pass withholds a row on page 1 only when the comment-keyed pass will claim it on a **later** page — i.e. its `comment_id` still resolves to a comment of this subject *and* is not among page 1's IDs. `ANTISPAMWIZARD_Privacy::comment_ids_on_later_pages()` answers that with the **same** `get_comments()` query as `get_comment_ids()` (`author_email` + `comment__in`, `status => 'any'`), so "a comment of this subject" is decided identically in both places; a `comment_id` of 0, a hard-deleted comment and another subject's comment are all unreachable that way and are exported by hash. Deciding the split from the **row IDs another page's hash query returned** is what cannot work, and is the bug this replaced: a hash read that failed on page 1 and succeeded on page 2 had page 2 recognise the row as hash-matched and skip it while page 1 never emitted it, so the full comment text reached no page at all in a report still marked `done` (`PrivacyTest::test_export_emits_a_hash_matched_sample_on_a_later_page_when_the_page_one_hash_lookup_failed` pins it). Every remaining failure mode costs a duplicate, never an omission: `find_by_email_hash()` reports a failed read as an empty array, so nothing is withheld that the comment-keyed pass will not emit, and a reachability lookup that comes back empty makes page 1 emit the row as well as the page its comment falls on. `…test_export_does_not_repeat_a_hash_matched_sample_on_a_later_comment_page` pins the exactly-once split across both pages (and that rows predating the `email_hash` column still export on their comment's page); `…test_export_still_emits_a_hash_matched_sample_when_the_hash_lookup_returns_nothing` and `…_on_a_later_page_when_the_hash_lookup_returns_nothing` pin the failed-read behaviour through an injected repository whose hash lookup always comes back empty. `find_by_email_hash()` selects the same columns as `find_by_comment_ids()` — the two results are merged into one array keyed by row `id`, so a row fetched by either key must carry the same keys (`SampleRepositoryTest::test_email_hash_queries_backtick_quote_the_table_name` pins the column list). Both `export()` and `erase()` normalise `$page = max( 1, $page )` up front so the two notions of "page" agree: `get_comment_ids()` already clamped, while the hash-keyed lookups test `1 === $page`, so a page of 0 processed the comment-keyed data and skipped every hash-keyed row while still reporting the request done (`…test_export_treats_page_zero_as_page_one_for_hash_keyed_data` and its `erase` twin pin it); each item carries date added, training category rendered through the existing `Spam`/`Ham` msgids, and the **full** stored comment text (unlike the spam-log fragment). `erase()` calls `delete_by_comment_ids()` and, on page 1, `delete_by_email_hash()`. When either actually removed rows it then purges the cached model units through `ANTISPAMWIZARD_Model_Store::delete_units( ANTISPAMWIZARD_Model_Store::unit_keys() )`: a unit carries the trained comment's text as a token list, so leaving it cached would keep a readable copy of the erased text in `wp_options` for up to a day after the request reported success, which the policy text's “until it is erased through a personal-data erasure request” promise does not allow. Both calls are static and the key list is exhaustive — that is what a unit key naming the unit rather than fingerprinting its samples buys, and why the keys no longer have to be taken before the delete. All eleven keys go rather than only the affected script's, because the combined unit holds every script's samples and the erased rows' scripts are not known here. The purge runs when this page removed a sample **or** whenever this is **page 1**, whatever it deleted: the retry the "please retry this erasure request" message asks for finds the sample rows already gone, so a purge gated on the request's own deletions would be skipped and the second request would close clean over the unit the first could not drop — and gating it on a durable record of the first failure instead would put that promise behind the very option store whose refusal is the failure being recorded. A later page leaves the cache alone unless it deleted something, so one paginated request flushes once, and the cost of the page-1 rule is a single model-cache flush per erasure request — a rare, admin-approved event — paid by the next comment in each script as a cold rebuild. `PrivacyTest::test_erase_purges_the_model_units_cached_from_the_erased_sample`, `…test_erase_purges_the_model_cache_on_page_one_whatever_it_removed` and `…test_a_retried_erasure_purges_units_the_first_attempt_could_not_drop` pin it. A purge `ANTISPAMWIZARD_Model_Store::delete_units()` reports as incomplete — meaning training text is still stored after every lever, not merely that a key survived — sets `items_retained` and emits the same message a refused sample DELETE does — the cached copy is the erased text just as much as the row was — reusing the existing msgid rather than adding a POT entry (`…test_erase_retains_items_when_the_model_cache_purge_fails` and `…test_erase_does_not_retain_items_when_the_cache_purge_succeeds` pin it). The hash path is what covers a sample whose source comment was hard-deleted — emptying the spam queue does that to exactly the comments samples are trained from, and without it the retained full text would be permanently undiscoverable. Both skip silently when `ANTISPAMWIZARD::get_instance()->get_repository()` is null. Those two deleters return `int|false`; a `false` sets `items_retained => true` and adds a "could not be removed because of a database error" message, because collapsing a failed DELETE into "nothing matched" would close an erasure request while the full comment text is still stored (`PrivacyTest::test_erase_retains_items_when_the_sample_delete_fails` and `…does_not_retain_items_when_nothing_matched` pin both sides). Paginates 50 comments/page. Registered unconditionally from `ANTISPAMWIZARD::init()` (the filters are inert outside privacy/cron requests). The **eraser is registered at priority 5**, ahead of core's `wordpress-comments` eraser (priority 10, `wp-includes/default-filters.php`): WordPress runs erasers strictly in array order, one eraser's pages at a time, and core's blanks `comment_author_email` on every comment it anonymizes — so at priority 10+ the subject lookup would find no comments and this eraser would remove nothing while still reporting the request complete. Core skips `spam`/`trash` (its `get_comments()` uses the default `all` status), so only comments the site later moved out of the spam queue are affected — exactly the false positives a person files an erasure request about. `PrivacyTest::test_eraser_is_registered_ahead_of_cores_comment_eraser` pins it

## `ANTISPAMWIZARD_CF7_Integration`

soft dependency on Contact Form 7; registered on `plugins_loaded` only when `WPCF7_ContactForm` and `WPCF7_Submission` exist (`ANTISPAMWIZARD_CF7_Integration::is_available()`). Hooks `wpcf7_form_elements` at priority 100 to append bot-check fields, `wpcf7_enqueue_styles` to enqueue `public/css/comment-form.css` (`ANTISPAMWIZARD_VERSION`), and `wpcf7_spam` (10, 2, with `$submission = null` fallback to `WPCF7_Submission::get_instance()` and upstream `$spam` passthrough) to run the shared detector. Token is bound to the contact-form post ID (`WPCF7_ContactForm::get_current()->id()` at render, `$submission->get_contact_form()->id()` at submit, injected as `comment_post_ID`) so render/submit mismatch is impossible; adapter `collect_submission()` builds `comment_content` from `text`/`textarea` basetypes joined with `"\n\n"` (excluding email/url/tel/select/checkbox etc.), `comment_author_email` from the first valid `email` basetype value, `comment_author` from the first `text` value, and `comment_author_IP` from `get_meta('remote_ip')` with `comment_type` left unset so all checks run; all failure modes are fail-open and the whole `filter_spam()` body is `try/catch(\Throwable)` so a CF7 API surprise can never flag or fatal. Flagged submissions are logged with `source => 'form'` and a salted SHA-256 email hash (via `ANTISPAMWIZARD_Detector::hash_email()`) and emitted to `add_spam_log()` when available.
