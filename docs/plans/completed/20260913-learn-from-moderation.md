# Learn from moderation: train on WordPress Spam / Not Spam, and a "Mark as spam" link under comments

## Overview

Today the only way to teach the classifier is the Spam/Ham pills inside the plugin's own Spam Log, which lists only comments the plugin already blocked — so a comment that passed every check, the case that most needs teaching, has no way in. This adds one training point, the WordPress comment status transition, so every Spam / Not Spam decision made anywhere (Comments-screen row action, bulk action, Akismet, the plugin's own pill) trains the classifier; and a "Mark as spam" link rendered under each comment on the site for administrators, so a moderator can remove and teach in one action from the page where they see the spam.

A new `ASW_Moderation` class owns both. Training is locked once per comment and category by the existing Spam Log `trained_as` flag, so the AJAX pill and the transition it triggers together store exactly one sample, in either order. Samples are stored exactly as today — script detected from the text, whitespace-normalised content, keyed by `comment_id` and the salted `email_hash` — so the Privacy API exporter and eraser reach them unchanged and `uninstall.php` is untouched.

The plugin version stays 1.0.0 (it is not yet published to WordPress.org); the new changelog bullets fold into the existing `= 1.0.0 =` section.

- [x] Category flip: **after** a successful insert, call `$repository->delete_by_hash( $script, $opposite_category, hash( 'sha256', $content ) )` so a Spam → Not Spam decision (or the reverse) replaces the previous sample rather than leaving both. Inserting before deleting is deliberate — a failed insert must never leave the table short a row.
- [x] Failure rollback, keyed on what the claim returned, so the log never contradicts the table:

## Deviations from the plan (recorded during code review)

Two items above are no longer literally true of the shipped code, both deliberately:

- **`ASW_Admin_Page::ajax_mark_comment()`'s observable behaviour did change on its
  failure paths** (Task's "Related patterns" note said it must not). Making the pill
  and the transition it fires share one per-body lock and one sample table forced
  three changes that cannot be behaviour-preserving: it now reconciles the
  opposite-category row itself (nothing else does, when the comment is already at the
  target status and no transition fires); a failed status change **keeps** the sample
  it stored instead of deleting it (the table dedups on content, so that row can
  already have been adopted by a concurrent trainer's `'exists'`, and deleting it was
  a silent loss on another comment) while still reconciling the opposite row and
  releasing the claim; and every refused claim rollback is now reported to the
  moderator instead of being returned as a plain "try again" the pill would answer
  `'already_trained'`. The success path is unchanged, and `MarkCommentTest` covers
  each new failure path.
- **Task 5 lists three new msgids; there are four.** The fourth,
  `Training data may be inconsistent. Please check training data manually.`, is what
  the three non-status rollback failures report — the existing rollback msgid names a
  status change that, on those paths, did succeed. POT, all nine `.po` and all nine
  `.mo` carry it.
